## 1. Что такое Fumox

**Fumox** это легкий сервис агрегации прокси-подписок, написанный на Rust. Вы
указываете ему любое количество *источников* (URL, возвращающих списки
прокси-ссылок), а Fumox превращает этот хаос в чистые, отфильтрованные
подписки, которые можно сразу вставить в прокси-клиент (v2rayN, Nekobox,
Clash/Mihomo, sing-box и подобные).

Конкретно Fumox:

- **Скачивает** источники по расписанию (или по запросу), прозрачно
  декодируя base64 и автоматически определяя формат входа (URI-списки,
  Clash YAML, sing-box JSON).
- **Разбирает** каждую прокси-строку в нормализованную модель. Поддерживаемые
  протоколы: `vless`, `vmess`, `trojan`, `ss` (Shadowsocks), `hysteria2`,
  `tuic`, `mieru`, `socks5`, `naive+https`, `snell`, `anytls`. Нераспознанные
  параметры переносятся как есть: ничего не теряется. Учтите, что у sing-box
  нет исходящего типа для Snell и AnyTLS, поэтому в выгрузке sing-box эти
  прокси просто не попадают, вместо того чтобы подсунуть блок, который
  нельзя запустить; выгрузки Clash и URI несут их полностью.
- **Обрабатывает** прокси через настраиваемый конвейер: фильтры по протоколам,
  переименование по regex, гео-теги с флагами стран, фильтрация по живучести,
  дедупликация, сортировка.
- **Проверяет живучесть** прокси в фоне: мертвые узлы автоматически уходят в
  карантин и исчезают из подписок; восстановившиеся возвращаются.
- **Отдает** результат по HTTP в формате, который понимает ваш клиент:
  обычный URI-список, base64, Clash/Mihomo YAML или sing-box JSON.

Что это дает на практике:

| Без Fumox                                                                       | С Fumox                                        |
| ------------------------------------------------------------------------------- | ---------------------------------------------- |
| Десяток URL подписок, каждая из которых умирает или меняется без предупреждения | Один стабильный URL на каждый случай           |
| Мертвые прокси висят в клиенте, пока вы не заметите                             | Мертвые прокси автоматически уходят в карантин |
| Один и тот же узел трижды под разными именами                                   | Дубликаты сливаются по всем источникам         |
| Имена вида `relay-01-xyz`                                                       | Имена вида `🇩🇪 Germany · relay-01-xyz`          |
| Один формат на источник                                                         | Один формат на профиль – выбираете вы          |

## 2. Как это работает

Fumox устроен как Cargo-workspace из трех крейтов с одним внешним помощником:

| Компонент      | Тип             | Что делает                                                                                                                                                                               |
| -------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fumox-core`   | библиотека      | Общие модели данных, SQLite-хранилище и миграции, парсеры/сериализаторы протоколов, гео-резолвер, фингерпринты, загрузка конфигурации                                                    |
| `fumox-server` | бинарник        | Скачивает источники, выполняет конвейер обработки, отдает подписки (`/sub`, `/src`) и админ-панель                                                                                       |
| `fumox-probe`  | бинарник        | Демон проверки живучести: проверяет прокси и управляет их жизненным циклом (alive / quarantine / removed)                                                                                |
| **meow-rs**    | внешний процесс | Прокси-ядро, совместимое с mihomo/Clash, с REST API. Probe использует его для настоящих туннельных проверок (T2). Fumox не устанавливает и не запускает его: только обращается к его API |

Все компоненты используют одну базу SQLite в режиме WAL: это единственный
источник истины. In-memory кэши существуют лишь для ускорения ответов.

```mermaid
flowchart LR
    SRC["Источники подписок<br/>(URL со списками прокси)"] -->|периодическая загрузка| SRV
    SRV["<b>fumox-server</b><br/>parse → pipeline → encode"] <--> DB[("SQLite (WAL)<br/>sources · proxies<br/>profiles · logs")]
    DB <--> PROBE["<b>fumox-probe</b><br/>демон проверки живучести"]
    PROBE <-->|"T2-проверки туннелем<br/>(REST API)"| MEOW["<b>meow-rs</b><br/>прокси-ядро"]
    SRV -->|"GET /sub/{id} · GET /src/{id}"| CLIENT["Ваш прокси-клиент<br/>(Clash, v2rayN, sing-box…)"]
    ADMIN["Админ-панель<br/>http://127.0.0.1:8081"] --> SRV
```

**Путь запроса.** Когда прокси-клиент опрашивает `GET /sub/{token}`, сервер
собирает источники профиля, применяет конвейер (фильтры → переименование →
гео → health-фильтр → дедупликация → сортировка), кодирует результат в
выходной формат профиля и отвечает. Готовый результат кэшируется, поэтому
большинство запросов обслуживается из памяти; кэш обновляется в фоне
(stale-while-revalidate).

**Фоновый цикл.** Независимо от запросов `fumox-server` запускает планировщик,
который периодически перезагружает каждый включенный источник, сверяет
разобранные прокси с базой (новые → вставить, исчезнувшие → отвязать; пока
probe подтверждает `alive`-прокси, он остается привязанным (см. alive-linger
в [разделе 10](#10-проверка-живучести-и-жизненный-цикл-прокси), вернувшиеся →
обновить только поля-идентичность) и журналирует каждую загрузку. Тем временем
`fumox-probe` выбирает прокси и обновляет их статус живучести, который затем
использует health-фильтр.

Два правила не дают этому циклу долбить сломанный источник. Источник, у
которого последняя попытка провалилась, откладывается на растущий backoff — две
минуты после первой неудачи, вдвое больше после следующей, максимум час — так
что мёртвый URL не опрашивается на каждом тике; оживший источник подхватывается,
как только истёк его backoff. И каждая загрузка идёт под бюджетом, посчитанным
из таймаутов загрузки (`[fetch].connect_timeout_secs`,
`[fetch].read_timeout_secs` и число повторов): попытка, которая его превысила,
прерывается, её слот освобождается, а ошибка уходит в админ-панель вместо того,
чтобы блокировать цикл.

Журнальная очистка выполняется и на стороне сервера: `fetch_log` и
`probe_requests` проходятся с каденцией `[probe].retention_interval_secs` и с
теми же окнами, что использует probe-демон (`[retention]`). Развёртывание с
демоном и без него остаются ограниченными одинаково.

Сетевых слушателя два, и они намеренно разделены:

| Слушатель | Адрес по умолчанию | Отдает                                           | Виден из сети?                                                        |
| --------- | ------------------ | ------------------------------------------------ | --------------------------------------------------------------------- |
| Публичный | `0.0.0.0:8080`     | `GET /sub/{id}`, `GET /src/{id}`, `GET /healthz` | Да – именно его опрашивают клиенты                                    |
| Админка   | `127.0.0.1:8081`   | Админ-панель (`/admin/*`)                        | Нет – только loopback; доступ через SSH-туннель или TLS reverse-proxy |

## 3. Ключевые понятия

| Понятие                    | Значение                                                                                                                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Источник (source)**      | URL подписки и настройки его загрузки (TTL, кодировка, заголовки, pipeline).                                                                                                         |
| **Прокси (proxy)**         | Одна нормализованная прокси-запись. Идентичность задает *фингерпринт*, а не имя.                                                                                                     |
| **Фингерпринт**            | `sha256(scheme \| нормализованный host \| port \| credential \| security-параметры)`. Отображаемое имя намеренно не входит, поэтому переименование никогда не создает дубликатов. Каноническая форма несет версию, поэтому релиз, который ее меняет, меняет все ключи — см. ниже. |
| **Профиль (profile)**      | Именованный набор источников + правила обработки + выходной формат. У каждого профиля свой эндпоинт `/sub/{id или slug}`; именно этот URL вы вставляете в клиент.                    |
| **Slug**                   | Необязательный человекочитаемый идентификатор источника или профиля (`/sub/my-list` вместо `/sub/nNqRYHbOSqM5`).                                                                     |
| **Pipeline**               | JSON-правила, описывающие, как прокси фильтруются, переименовываются, получают гео-теги, дедуплицируются и сортируются. У источника свой pipeline; профиль может его переопределить. |
| **Статус**                 | Состояние живучести прокси: `unknown`, `alive`, `ready`, `quarantine`, `removed` (см. [раздел 10](#10-проверка-живучести-и-жизненный-цикл-прокси)).                                           |
| **Карантин и второй шанс** | Прокси, который стабильно не проходит проверки, исключается из выдачи, а затем получает повторную проверку через настраиваемую задержку второго шанса (по умолчанию 12–16 часов) до принятия окончательного решения. |
| **T1 / T2**                | Два уровня проверки живучести: T1 = прямая TCP/TLS-доступность; T2 = настоящий туннельный запрос через meow-rs.                                                                      |

Идентификаторы и токены эндпоинтов имеют вид строк `nanoid(12)` из алфавита
`A-Za-z0-9_-` (72 бита энтропии, перебор бессмысленен).

Пять статусов образуют небольшую иерархию. `unknown` — прокси, у которого еще
нет вердикта: его либо не проверяли, либо проверять нечем (схема не
проверяется активным пробником). `alive` — успешная проверка TCP/TLS, то есть
прямая доступность узла. `ready` — успешная более сильной проверки: настоящий
туннельный запрос через meow-rs, то есть прокси действительно выпускает
трафик. Прокси в `ready` до этого был `alive`, и провал туннельной проверки
возвращает его в `alive` (см.
[раздел 10](#10-проверка-живучести-и-жизненный-цикл-прокси)). `quarantine` и
`removed` — два состояния, которые убирают прокси из выдачи.

Ярусы не пересекаются: `alive` и `ready` — это вычисляемые уровни, а
не отдельные поля записи, и один прокси находится ровно в одном из них. Две
ссылки экспорта идут ровно по этой иерархии: `/export/alive/{token}` отдает
ярус `alive`, `/export/ready/{token}` — ярус `ready` (то есть подтвержденные
туннелем прокси, среди которых есть и hysteria2), так что прокси в `ready`
попадает только во вторую ссылку и никогда — в первую.
`health.exclude_statuses`
пайплайна (по умолчанию `["quarantine", "removed"]`) решает, что профиль
выбрасывает из своей выдачи: по умолчанию выбрасываются оба снятых состояния,
а `unknown`, `alive` и `ready` проходят — поэтому `/sub` может отдать прокси,
которого еще никто не проверял.

Каноническая форма фингерпринта несет версию, поэтому релиз, который эту
форму меняет, меняет все ключи. Сервер один раз пересчитывает сохраненные
ключи — при первом старте после такого обновления, до первой загрузки
источников: прокси сохраняет свою строку, а вместе с ней статус, задержку,
гео-данные и историю проверок, поэтому новый ключ не виден ни панели, ни
клиентам. Прокси, который фид публиковал в двух написаниях, до обновления
лежал в двух строках; пересчет сливает их в одну. Выживает та строка,
которую уже оценил probe, ссылки на источники обеих строк переезжают на
нее, история проверок обеих строк следует за прокси, а недостающее в
выжившей строке состояние берется из исчезающей. Прокси, который probe
вывел из обращения, сохраняет свой вердикт при слиянии; он возвращается
через существующие для этого пути (`[ingest].removed_as_unknown` возвращает
выведенный из обращения прокси, который фид все еще несет, кнопки *Revive*
в панели — выведенную из обращения популяцию). После пересчета никакие две
строки не описывают один и тот же прокси, поэтому один узел не может быть
выдан дважды.

## 4. Быстрый старт

Три способа запустить Fumox. Рекомендуемый способ: Docker Compose. Одна команда
поднимает сервер, probe-демон и ядро meow-rs, уже связанные между собой.
Используете Podman вместо Docker? Тот же стек разворачивается как podman-под
под управлением systemd через quadlet-юниты (см.
[`docker/README.ru.md`](./docker/README.ru.md)).

### Вариант A – Docker Compose (рекомендуется)

Требования: Docker с плагином Compose.

```bash
git clone https://github.com/Viktor45/fumox.git
cd fumox

cp .env.example .env
# отредактируйте .env: задайте настоящий FUMOX_ADMIN__TOKEN (секрет входа в админку)
# если панель открывается по plain HTTP (http://127.0.0.1:8081), задайте также
# FUMOX_ADMIN__SECURE_COOKIES=false — compose ставит true, а браузер молча
# выбрасывает такую cookie сессии

docker compose up -d          # готовые образы из GHCR, самый быстрый путь
docker compose up -d --build  # ...или сборка server и meow-обертки из исходников
```

Первая команда тянет опубликованные образы, закрепленные по digest:
по умолчанию compose берет `FUMOX_IMAGE`/`FUMOX_MEOW_IMAGE` из `.env`,
а без них — digest из строк `image:` в `docker-compose.yml` (один digest —
один неизменяемый манифест, поэтому развернутый стек не меняется под
собой); с `--build` server и meow-обертка собираются локально (`Dockerfile`
в корне и `docker/meow/Dockerfile`). Обновление до нового релиза — это
подмена закрепления: впишите в `.env` новые `FUMOX_IMAGE` и `FUMOX_MEOW_IMAGE`
(digest, либо тег нового релиза) и выполните `docker compose pull &&
docker compose up -d`; сам по себе `pull` ничего не обновляет — закрепление
в `.env`/compose само не двигается. Тег `latest` обновляется при пуше тега
новейшего стабильного релиза на коммит, достижимый из `main`, и при ручном
запуске workflow (workflow_dispatch) с ветки `main`; запуск с другой ветки
добавляет лишь теги ref/sha и `latest` не трогает.

Готово. Что вы получаете:

- Подписки: `http://<host>:8080/sub/{id}`
- Админ-панель: <http://127.0.0.1:8081/admin> (вход по токену из `.env`)
- Три контейнера: `server` (fumox-server), `probe` (fumox-probe), `meow`
  (ядро meow-rs для T2-проверок туннелем)

Полезные переменные `.env` (все, кроме токена, необязательны):

| Переменная                        | По умолчанию                          | Назначение                                                                                                                                                                                                    |
| --------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Замечания:

- Порт админки публикуется только на `127.0.0.1`. Чтобы зайти с другой
  машины, используйте SSH-туннель (`ssh -L 8081:127.0.0.1:8081 host`) или
  TLS reverse-proxy. Готовый пример такого прокси: `docker/nginx/`:
  контейнер nginx с TLS-терминацией для `/sub` и `/admin` (сертификаты
  монтируются в `/certs`, ACME-челленджи обслуживаются на 80-м);
  подключается сервисом в `docker-compose.yml` перед `server`.

> **За reverse-proxy обязательно задайте три ключа**, чтобы per-IP rate
> limit и `Host`-allowlist работали корректно:
>
> - `[server].trust_proxy_ips` / `[admin].trust_proxy_ips`: CIDR
>   прокси-сервера (`["127.0.0.1/32"]`, если nginx на том же хосте).
>   Без этих ключей все запросы приходят с IP прокси и лимит схлопывается
>   в один общий бюджет. То же самое происходит, когда перед сервером
>   стоит **несколько** прокси и в списке доверия — все они: сервер
>   обходит заголовок от соседа наружу и пропускает доверенные хопы,
>   поэтому недоверенного адреса не остается и ключом становится адрес
>   ближайшего хопа — один ключ rate-limit на весь поток. Перечислите
>   в `trust_proxy_ips` каждый прокси цепочки **и** поднимите лимит,
>   который этот ключ делит (`[server].rate_limit`,
>   `[admin].rate_limit`), иначе все клиенты за цепочкой тратят бюджет
>   одного адреса.
> - `[server].trust_proxy_header` / `[admin].trust_proxy_header`: семейство
>   заголовков, которое пишет прокси, — `"xff"` для `X-Forwarded-For` /
>   `X-Forwarded-Proto` / `X-Forwarded-Host`, `"forwarded"` для RFC 7239
>   `Forwarded`, `"both"` если прокси шлёт оба. По умолчанию `"none"`:
>   forwarding-заголовки не читаются вовсе, ведь это текст, который
>   выбрал клиент, — подделав его, клиент выбирал бы себе же отдельное
>   окно rate-limit и отдельную подсказку схемы. Укажите семейство,
>   которое действительно пишет ваш прокси.
> - `[server].allowed_hosts` / `[admin].allowed_hosts`: публичное имя
>   хоста (`["fumox.example.com"]`). Без этих ключей `Host`-заголовок
>   принимается как есть: атакующий, способный подменить `Host`,
>   добьется того, что админка отрисует URL на его домен и
>   скомпрометирует токены `/export/alive/{token}` /
>   `/export/ready/{token}`. По умолчанию оба ключа равны `[]`, чтобы
>   сохранить историческое поведение при прямом соединении; для
>   любого reverse-proxy-развертывания оба ключа нужно задать.
>
> Два списка проверяются отдельно. Ссылку на alive/ready за
> *Импорт/экспорт*, *Источники* и *Профили* админка строит по тому
> хосту, по которому вы открыли панель, и эти три экрана
> отрисовываются при любом хосте. Поэтому если
> `[server].allowed_hosts` закреплен за публичным доменом, а панель вы
> открываете на её собственном loopback-адресе
> (`http://127.0.0.1:8081/admin`, именно это поставляет Compose), ссылка
> построится как `http://127.0.0.1:8080/...`, а публичный слушатель
> ответит на неё `404`: он не обслуживает этот хост. Либо заходите на
> панель по тому же имени хоста, которое разрешено публичным списком,
> либо добавьте `127.0.0.1` ещё и в `[server].allowed_hosts`.
>
> Allowlist применяется на входе админ-слушателя: запрос, чей `Host`
> не входит в `[admin].allowed_hosts`, отклоняется с `400` на любом
> маршруте панели, включая экран входа. За доверенным прокси
> дополнительно принимается пересланный хост
> (`X-Forwarded-Host` или `Forwarded: host=`, читается только из
> объявленного семейства), поэтому прокси, подменяющий `Host` именем
> своего upstream, продолжает работать.
>
> Админка также отвечает `403` (`err.cross_site`) на запросы,
> классифицированные как кросс-сайтовые: `Sec-Fetch-Site: cross-site`
> (переходы верхнего уровня на `/admin` исключены), `Origin: null`
> либо `Origin`, чей host:port не совпадает с заголовком `Host`.
> Браузеры с собственного источника панели и клиенты без заголовков
> (curl, мониторинг) не затронуты. Для reverse-proxy это добавляет то
> же требование, что и `Host`-allowlist выше: прокси должен пробрасывать
> `Host` без изменений (готовый пример `docker/nginx/` так делает:
> `proxy_set_header Host $host`). Легитимная не-браузерная интеграция,
> которая POST-ит в панель с заголовком `Origin`, должна слать родной
> источнику панели `Origin` или не слать его вовсе.
- База SQLite живет в томе `fumox-data`. Каталог `./config` монтируется в
  контейнер сервера **на чтение и запись** по умолчанию, чтобы страница
  *Править настройки* могла сохранять `app.toml`; задайте
  `FUMOX_CONFIG_ACCESS=ro`, чтобы закрепить его только на чтение (тогда
  страница правки становится read-only). Контейнер probe всегда монтирует его
  как `:ro`. Под Compose базы GeoLite2 лежат **не** там, см.
  [раздел 11](#11-гео-обогащение).
- meow-rs не публикует официального Docker-образа, поэтому маленькая обертка
  (`docker/meow/Dockerfile`) вокруг релизного бинарника либо тянется готовой
  из GHCR, либо собирается в режиме `--build`; публикуется она вручную,
  workflow'ом `docker-meow.yml` (см. Вариант B). Ее REST API (порт 9090)
  доступен только probe во внутренней сети.
- **Обновление движка.** Fumox работает с meow-rs через небольшой и стабильный
  срез REST API (`GET /version`, `PUT /configs`, `GET /proxies/{name}/delay`),
  и этот срез не меняется от релиза к релизу: в 0.21.2 → 0.22.0 набор из 26
  маршрутов, параметры проверки задержки и семантика 404/504/503 остались
  прежними, поэтому обновление сводится к пересборке образа, а не правка кода.
  Новый релиз upstream подхватывается правкой трех значений сразу: тега
  `MEOW_VERSION` и двух сумм `MEOW_SHA256_*` архивов релиза — в `.env` для
  локальной сборки и в `docker/meow/Dockerfile` (плюс входы workflow) для
  публикуемого образа. `latest` отвергается на обоих путях: обертка,
  уезжающая сама, делает образ непроверяемым. Работающее ядро называет себя
  само: `docker compose exec meow meow -v` печатает `Meow Meta <версия>` —
  `0.27.0` у релиза, который закреплен в образе сегодня. Учтите, что 0.22.0 заменил rustls
  на BoringSSL во всём рантайме и сделал ключ `ipv6` действующим, см.
  `[meow].ipv6` ниже.
- **Что апгрейд до 0.22.0 сразу дает T2**, без правок в Fumox: транспорт
  `xhttp` стал настоящей исходящей (в 0.21.x XHTTP не было вовсе, такие записи
  нельзя было проверить), а SIP003-плагины Shadowsocks (`shadow-tls`, `restls`,
  `jls`, `kcptun`, `gost-plugin`) выполняются в процессе вместо запуска
  вспомогательного бинарника: образ `fumox-meow` содержит только сам `meow`,
  поэтому такие записи, ранее падавшие в T2, теперь работают. И то и другое
  Fumox уже корректно рендерил; способность появилась именно у движка.
- **Одноразовый дымовой стенд:** `scripts/smoke-up.sh` поднимает тот же стек
  вторым изолированным compose-проектом (`fumox-smoke`) на сдвинутых портах
  (18080 публичный / 18081 админка; переопределяются `SMOKE_PUBLIC_PORT` /
  `SMOKE_BIND` и `SMOKE_ADMIN_PORT`), генерирует собственный токен админки, дожидается
  старта и прогоняет базовые проверки (`/healthz`, страница входа в админку,
  404 от неверного токена alive-выгрузки, все три контейнера в состоянии
  `running` без перезапусков; проверка не зависит от настроенных уровней
  логов). Сгенерированный токен пишется в приватный файл с правами `0600`,
  путь к которому печатает скрипт; с флагом `--show-token` печатается сам
  токен. Токен, переданный через `FUMOX_ADMIN__TOKEN`, используется как есть
  и нигде не печатается и не записывается.
  `scripts/smoke-down.sh` сворачивает стенд (тома сохраняются, если не указан
  `--purge-volumes`). Основной стенд не затрагивается; оба стенда делят теги
  образов (`ghcr.io/viktor45/fumox:latest`,
  `ghcr.io/viktor45/fumox-meow:latest`), так что сборка стенда заодно
  обновляет образы и для основного.

### Вариант B – Готовый контейнерный образ

CI публикует мультиархитектурный образ (`linux/amd64` + `linux/arm64`, каждая
платформа снабжена аттестацией происхождения сборки) в GHCR **по тегам `v*`
и вручную через `workflow_dispatch`**; см. `.github/workflows/docker.yml`:
`ghcr.io/viktor45/fumox`. Пуш стабильного тега вроде `v0.2.0` на коммит,
достижимый из `main`, добавляет `0.2.0` и `sha-<короткий хеш>`. Тег `0.2`
обновляется только для новейшего релиза своей серии, а `latest` только для
новейшего стабильного релиза. Ручной запуск с `main` добавляет `main`,
`sha-<короткий хеш>` и `latest`; запуск с другой ветки добавляет
`branch-<ветка>` и `sha-<короткий хеш>`, без `latest`.
Автоматической сборки по push в `main` нет. В образе **оба** бинарника:
сервер идет командой по умолчанию, а probe задается переопределением команды.

```bash
# Сервер
docker run -d --name fumox \
  -e FUMOX_ADMIN__TOKEN=<secret> \
  -v fumox-config:/app/config -v fumox-data:/app/data \
  -p 8080:8080 -p 127.0.0.1:8081:8081 \
  ghcr.io/viktor45/fumox

# Probe (тот же образ, те же тома; fumox-probe это аргумент команды,
# tini остается entrypoint)
docker run -d --name fumox-probe \
  -v fumox-config:/app/config -v fumox-data:/app/data \
  ghcr.io/viktor45/fumox fumox-probe
```

Внутри образа: конфигурация читается из `/app/config/app.toml` (если
смонтирован), база `/app/data/fumox.db`, слушатель админки заранее задан как
`0.0.0.0:8081` (compose-файл публикует его только на loopback). HTTP-клиента
(curl/wget) в образе нет, health-пробы оркестратора направляйте на
`GET /healthz` порта 8080.

**Строка с токеном не декоративная.** Без `FUMOX_ADMIN__TOKEN=<secret>` панель
не поднимается: встроенный дефолт `change-me` паролем не считается, слушатель
админки не стартует, и `/admin` отвечает 404. Задайте случайное значение —
`printf 'FUMOX_ADMIN__TOKEN=%s\n' "$(openssl rand -hex 32)"`.

**meow-rs в этом образе нет.** Образ содержит только два бинарника Fumox; ядро
T2 — отдельный контейнер (`ghcr.io/viktor45/fumox-meow`, публикуется вручную,
см. следующий абзац). Запустите его сами, дайте probe общий том для
сгенерированного конфига (`[meow].config_path` должен быть путем, который
meow-rs сам прочитает), укажите адрес ядра в `[meow].api_addr` и задайте
секрет контроллера (`FUMOX_MEOW__API_TOKEN`) — ядро отвергает все остальное.
Без работающего meow-rs работают только проверки T1: ни один прокси не
достигает яруса `ready`, вердикты T2 не приходят вовсе, а probe держит паузу с
backoff, а не записывает прокси в отказы по отсутствию ядра. Схему соединений
показывает стек из Варианта A.

Обертка meow-rs (`docker/meow/Dockerfile`) тоже есть в GHCR,
`ghcr.io/viktor45/fumox-meow`, но публикуется **только вручную**: workflow
`docker-meow.yml` не запускается ни по push, ни по тегам, его запускают из
вкладки Actions (вход `meow_version` принимает явный тег вроде `v0.27.0` —
`latest` отвергается — вместе с двумя суммами `meow_sha256_*` архивов
релиза). Каждый запуск публикует значение `meow_version` и
`sha-<короткий хеш>`. Запуск с `main` также обновляет `main` и `latest`;
другие ветки добавляют `branch-<ветка>`, не меняя `latest`. Аттестация та же,
по каждой платформе. Стек из Варианта A уже ссылается на этот образ:
`docker compose up -d` тянет его,
`--build` собирает обертку локально (переменная `.env` `MEOW_VERSION` и две
суммы выбирают релиз только в режиме сборки).

### Вариант C – Сборка из исходников

Требования:

- Rust-тулчейн **≥ 1.98** (edition 2024).
- Системный dev-пакет SQLite: sqlx линкует системную библиотеку, а не
  встроенную. Debian/Ubuntu: `sudo apt install libsqlite3-dev pkg-config`.
- OpenSSL не нужен (rustls), фронтенд-сборки нет.

```bash
cargo build --release
# бинарники: target/release/fumox-server и target/release/fumox-probe

./target/release/fumox-server            # подписки + админ-панель
./target/release/fumox-probe             # демон проверки живучести (отдельный процесс)
```

Опции командной строки, по бинарникам — они неодинаковые: только у
`fumox-server` есть `--health-check`:

```
fumox-server [OPTIONS]

Options:
  -c, --config <CONFIG>  Путь к TOML-файлу конфигурации (сильнее FUMOX_CONFIG)
      --health-check     Проверить /healthz работающего сервера и завершиться
                         с кодом 0 при ответе 200, иначе 1. Запрос уходит на
                         адрес публичного bind'а из конфига (для wildcard —
                         на loopback той же семьи: 127.0.0.1 для 0.0.0.0,
                         ::1 для ::), на порт этого bind'а.
                         Используется как healthcheck контейнера
                         (`docker-compose.yml` прописывает его в `test:`):
                         в runtime-образе нет ни curl, ни wget.
  -h, --help             Справка
  -V, --version          Версия

fumox-probe [OPTIONS]

Options:
  -c, --config <CONFIG>  Путь к TOML-файлу конфигурации (сильнее FUMOX_CONFIG)
  -h, --help             Справка
  -V, --version          Версия
```

Это весь CLI, все остальное настраивается конфигурацией (путь к TOML-файлу
можно также задать переменной окружения `FUMOX_CONFIG`; без флага и
переменной используется `config/app.toml`, если существует; полная схема
слоев описана в [разделе 8](#как-разрешается-конфигурация)). Сервер при старте
создает базу и применяет миграции, затем работает до SIGINT/SIGTERM
(корректное завершение). Дренаж после сигнала ограничен по времени: слушатели
перестают принимать соединения и дорабатывают открытые запросы не дольше
10 секунд, после чего оставшиеся соединения обрываются. Без этой границы один
SSE-поток в админке или медленная выгрузка могли держать процесс живым до
тех пор, пока его не убил супервизор. Probe вообще не открывает слушающих сокетов.

Для быстрого запуска в режиме разработки:

```bash
cargo run -p fumox-server
cargo run -p fumox-probe
```

## 5. Первая подписка – по шагам

Пятиминутный проход при работающем стеке ([быстрый старт](#4-быстрый-старт)).

1. **Вход.** Откройте <http://127.0.0.1:8081/admin> и введите
   `[admin].token` (значение `FUMOX_ADMIN__TOKEN`). При желании выберите язык
   на экране входа, выбор запомнится.

2. **Добавьте источник.** *Источники → Новый*. Вставьте URL подписки, дайте
   имя. Все остальное уже настроено разумно: кодировка `auto` (base64
   определяется автоматически), формат входа: авто-детект (URI-список /
   Clash YAML / sing-box JSON), TTL кэша 1 час. Если хост доступен только по одному семейству
   IP, задайте **семейство IP** (`ipv4`/`ipv6`) в форме, иначе оставьте
   «по умолчанию», чтобы действовала настройка `[fetch] ip_family`.
   Сохраните. Источник сразу будет загружен: вы увидите, сколько прокси
   найдено.

3. **Создайте профиль.** *Профили → Новый*. Дайте имя, отметьте источники,
   которые должны в него входить, выберите выходной формат:
   - `uri_list`: простой текст, по одной прокси-ссылке в строке (универсальный);
   - `base64`: тот же список в base64 (то, что ждут многие клиенты);
   - `clash`: конфиг Clash/Mihomo YAML;
   - `sing_box`: конфиг sing-box JSON.

   При желании задайте **slug** (тогда эндпоинт: `/sub/your-slug`) и
   **токен доступа** (тогда клиенты должны его передавать, см. ниже). Можно
   также перечислить **страны** (например: `DE, US`), чтобы отдавались только
   прокси этих стран (см. [Страновой фильтр](#страновой-фильтр)).

4. **Скопируйте URL.** В карточке профиля указан URL подписки, например
   `http://<host>:8080/sub/nNqRYHbOSqM5`. Если у профиля задан токен доступа,
   карточка об этом сообщает, а ссылка остаётся без токена — допишите
   `?token=…` (или отправьте заголовок `Authorization: Bearer …`) в
   прокси-клиенте. Вставьте полученную ссылку в клиент как подписку.

5. **Наблюдайте вживую.** Обзор показывает счётчики источников/прокси,
   недавние ошибки источников, панель **«Топ причин отказов»** за 24 ч и
   агрегаты по источникам: все топ-N регуляторы обзора объединены
   одним per-admin-cookie `fumox_dash_top_n` (5/10/15/25/50, по
   умолчанию 10); браузер *Прокси* показывает все узлы со статусом, страной и
   задержкой; страница *Probe* показывает пульс демона проверок и очередь
   карантина (истинное число, не размер превью). Обновления приходят в
   реальном времени через server-sent events.

Дальше Fumox сам перезагружает источники (по умолчанию раз в час), а probe
проверяет прокси. Мертвые узлы автоматически исчезают из подписки; больше
ничего не требует вашего внимания.

### Настройки источника

Поля формы источника и формат их значений:

| Поле                  | Формат значения                                                                                                    | Смысл                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Название              | строка, до 200 символов                                                                                           | как источник подписан в панели                                                                              |
| Slug                  | 2–64 символа: латиница, цифры, `-` и `_`, первый символ — буква или цифра                                           | адресная часть `/src/{slug}`; если поле пусто, используется id                                                |
| URL                   | `http(s)`-адрес подписки                                                                                          | откуда забирается фид; приватные адреса отвергаются, пока `[admin].allow_private_urls = false` (по умолчанию) |
| Включен               | флажок                                                                                                            | выключенный источник не опрашивается планировщиком и не попадает в выдачу                                    |
| Кодировка ответа      | `auto`, `plain`, `base64`                                                                                         | `auto` определяет кодировку по содержимому ответа                                                             |
| Формат входных данных | пусто (авто), `uri_list`, `clash_yaml`, `sing_box_json`                                                            | пусто = формат фида определяется автоматически                                                               |
| Семейство IP          | пусто (по умолчанию), `any`, `ipv4`, `ipv6`                                                                        | пусто = действует `[fetch].ip_family`; выбранное семейство строгое: нет адреса этого семейства — ошибка загрузки |
| Протоколы             | список имён схем: `vless`, `vmess`, `trojan`, `ss`, `hysteria2`, `tuic`, `mieru`, `socks5`, `naive`, `snell`, `anytls` | пусто = брать все; непустой список оставляет только эти схемы, остальные отбрасываются при инжесте           |
| TTL кэша              | целое число секунд, 60…86400, по умолчанию 3600                                                                   | период обновления источника и свежесть кэша                                                                 |
| Теги                  | список через запятую, например `paid, eu`                                                                         | метки для группировки источников в панели                                                                    |
| Заголовки             | по одному заголовку на строку в формате `Ключ: значение`                                                          | дополнительные HTTP-заголовки при загрузке; перекрывают `[fetch].user_agent`                                 |

TTL кэша — это и есть период планировщика: планировщик перезагружает источник,
когда с его последней успешной загрузки прошло не меньше TTL, а не «каждый час
по часам». Значение по умолчанию — 3600 секунд, то есть раз в час.

Значения заголовков в форме скрыты маской: неизменённое маскированное
значение сохраняется как есть, поэтому чтобы заменить его или использовать под
другим именем заголовка, введите значение заново.

## 6. Эндпоинты подписок

Все публичные эндпоинты живут на публичном слушателе (по умолчанию порт
**8080**).

| Эндпоинт                   | Описание                                                                                                                                     |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /sub/{id}`            | Объединенная подписка **профиля**. `{id}`: id профиля или его slug.                                                                          |
| `GET /src/{id}`            | Разобранные прокси **одного источника**. Health-фильтр выдачи действует и здесь: отдаются только живые уровни `alive` и `ready` — непроверенные (`unknown`), в карантине и удаленные не выдаются никогда, даже если health-фильтр конвейера их пропустил бы. `{id}`: id источника или slug. У источника может быть **собственный токен доступа** (см. ниже); токен профиля на `/src` не распространяется. |
| `GET /export/alive/{token}` | Все прокси яруса `alive` обычным `url_list` — именно этот ярус, а не «все живые прокси»: прокси в `ready` лежит в другом ярусе и отдается ссылкой `/export/ready`. `{token}`: токен ссылок экспорта. |
| `GET /export/ready/{token}` | Только ярус `ready` (прокси, у которых последняя проверка T2 прошла успешно, hysteria2 включительно). Тот же токен, тот же формат. |
| `GET /healthz`             | Проверка живости, возвращает `ok`.                                                                                                           |

### Две ссылки экспорта

`/export/alive/{token}` и `/export/ready/{token}` — это публичные ссылки
скачивания, которые показывает экран *Импорт и экспорт* в админ-панели. Это не
эндпоинты профиля и они не привязаны к профилю: у них один общий **токен
возможности** — случайный 12-символьный id, который создается при первом
старте и хранится в базе, поэтому ссылки переживают перезапуск. Панель
показывает обе ссылки и умеет заменить токен (*Перегенерировать ссылку*) —
один секрет, одна ротация, обе ссылки умирают одновременно. Неверный токен
даёт `404 link not found` — ровно то же, что и запрос с `Host` вне
`[server].allowed_hosts`, поэтому снаружи их не отличить.

Формат фиксирован: обычный `url_list` (`text/plain`) с блоком метаданных-
комментариев — никогда не base64, никогда не Clash, никогда не sing-box.
Параметр `?format=` отклоняется с `400`. Параметр `?download` превращает ответ
в файл (`fumox-alive-ГГГГ-ММ-ДД.txt` / `fumox-ready-ГГГГ-ММ-ДД.txt`).

Они ограничены дважды:

- **Не более `[server].export_max_rows` строк в теле** (по умолчанию 50 000).
  У этих двух ссылок нет ни собственного лимита на источник, ни лимита на
  профиль, поэтому именно этот ключ не дает одному скачиванию прочитать и
  отдать весь слой. Тело, которое урезал лимит, говорит об этом дважды: строкой
  `# truncated: showing 50000 of 81234 — raise [server].export_max_rows` в теле
  и заголовками `X-Fumox-Export-Truncated: true` и
  `X-Fumox-Export-Total: 81234` в ответе.
- **Кэш на 30 секунд**, поэтому пачка скачиваний внутри одного окна стоит
  одного рендера, а изменение статуса доходит до тела в пределах этого окна.

Обе границы, блок метаданных и счетчики слоев описаны подробно в
[разделе 7](#7-админ-панель).

Лимиты: ссылки живут на публичном слушателе, поэтому каждый запрос считается
в общий лимит на IP с запасом `[server].rate_limit` (по умолчанию `300/min`).
Строгое окно неудачных проверок токена `[server].auth_fail_rate_limit` (по
умолчанию `30/min`) относится к **токену профиля**, который отвечает `403`;
токен экспорта отвечает `404`, поэтому подбор от него попадает в лог как
неудачная проверка секрета, но это окно не исчерпывает.

### Токены доступа

По умолчанию эндпоинт профиля публичен для всех, кто знает URL, случайный
12-символьный id угадать невозможно. Для дополнительной защиты профилю можно
задать **токен доступа**: тогда каждый запрос должен его передавать: либо как

```
GET /sub/{id}?token=<токен_доступа>
```

либо в заголовке:

```
Authorization: Bearer <токен_доступа>
```

Нет токена или токен неверный → `403 Forbidden`. Неудачные проверки токена
ограничены по IP: после слишком многих попыток за минуту
(`auth_fail_rate_limit`, по умолчанию `30/min`) эндпоинт на время отвечает
`429 Too Many Requests`. Все публичные запросы дополнительно ограничены
общим лимитом на IP с запасом (`rate_limit`, по умолчанию `300/min`) против
скрейпа.

Токен хранится **в виде хэша** (SHA-256), а не открытым текстом: в файле
базы данных, в резервных копиях и в экспортированной конфигурации лежит
хэш, а не сам секрет. Что из этого следует:

- админ-панель больше не может показать токен — в форме правки стоит
  заполнитель; неизменённый заполнитель сохраняет токен, пустое поле
  снимает его;
- поэтому ссылка подписки в карточке профиля идёт без токена: допишите
  `?token=…` (или заголовок `Authorization: Bearer …`) сами;
- профили, защищённые до обновления, продолжают работать: строки со
  открытым токеном перезаписываются хэшем при следующем старте, а клиенты,
  которые уже знают токен, ничего не замечают.

**Источник** защищается так же: у формы источника есть собственный токен
доступа, и тогда `GET /src/{id}` требует его (`?token=…` или
`Authorization: Bearer`). Два токена независимы — токен доступа профиля
защищает только `/sub` и на `/src` **не** распространяется; источник без
собственного токена отдает данные публично, что бы ни требовали его профили.

### Выходные форматы

Формат это свойство профиля: один профиль, один формат. Query-параметр
`?format=` **не поддерживается** и возвращает `400`; если нужен тот же набор
прокси в другом формате, создайте второй профиль (это дешево).

| Формат     | Content-Type       | Примечания                                                       |
| ---------- | ------------------ | ---------------------------------------------------------------- |
| `uri_list` | `text/plain`       | Блок метаданных-комментариев, затем по одной прокси-URI в строке |
| `base64`   | `text/plain`       | URI-список в base64                                              |
| `clash`    | `text/yaml`        | Конфиг Clash/Mihomo, корневой ключ `proxies:`                    |
| `sing_box` | `application/json` | Конфиг sing-box, корневой ключ `outbounds:`                      |

Каждая выдача в чистом `uri_list` (`/sub` с форматом `uri_list`, `/src` и
экспорт живых прокси) начинается с небольшого блока комментариев, который
документирует файл: HTTP-заголовки теряются при копипасте или сохранении в
файл, а комментарии остаются с файлом:

```
# profile-title: Мой профиль
# profile-update-interval: 6
# nodes count: 42
# generated by: fumox 0.1.0 at 2026-09-03T18:05:07Z
```

`profile-update-interval`: рекомендованный интервал обновления в целых
часах (считается из cache TTL источников-членов; экспорт живых прокси
всегда дает `1`); `nodes count`: число строк-прокси, реально отданных;
строка `generated by` несет версию сервера и момент рендера тела в UTC.
Прокси-клиенты пропускают строки `#`, так что блок для них инертен, как и
для другого fumox, если скормить ему ссылку как источник. Профили в
формате base64 блока не получают: блоб должен оставаться чистым
закодированным списком.

Clash умеет представлять vless, vmess, trojan, ss, hysteria2, socks5, snell и
anytls; sing-box дополнительно не умеет snell и anytls, так что в его выгрузке
они пропускаются. Прокси остальных протоколов (tuic, mieru, naive) не
пропускаются с записью в лог, без ошибки. Совпадающие отображаемые имена получают автосуффиксы:
`Имя`, `Имя (2)`, `Имя (3)`…

Формат, который не умеет выразить запись, сообщает об этом, а не отдает молча
более короткий список: в ответе есть заголовок
`X-Fumox-Warning: incompatible-entries-skipped` и число пропущенных записей в
`X-Fumox-Skipped`, а в документе Clash — тот же счетчик комментарием
`# skipped: N (unsupported scheme)` (комментарий в YAML безвреден для парсеров
и переживает файл, скопированный из браузера, где заголовков уже нет). Заголовок
предупреждения может нести сразу несколько значений через запятую
(`parse-error, incompatible-entries-skipped`).

### Страновой фильтр

Профиль может ограничить выдачу конкретными странами: перечислите коды
ISO 3166-1 alpha-2 в поле **Страны** формы профиля (например: `DE, US`;
порядок и регистр не важны). Пока список непуст, `/sub` отдает только те
прокси, чья страна определена по GeoIP-базе; факты сохраняются при загрузке
источников и дозаполняются фоновым backfill-ом на старте.

Прокси, для которых страна **не определена**, при активном фильтре
исключаются: фильтр означает подтвержденные страны, а не все,
что не чужое. Пустой список выключает фильтр. Изменение списка действует
сразу: уже при следующем обновлении подписки клиентом выдача будет другой.

### Поведение ответов (что видит ваш клиент)

| Ситуация                                                                                          | Ответ                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Все в порядке                                                                                     | `200` + свежие данные                                                                                                                                                                                                                    |
| Часть источников временно недоступна (ошибки `network`, `http_server`)                            | `200` + последние хорошие данные упавших источников + свежие остальных; заголовок `X-Fumox-Stale: true`. Stale отдается столько, сколько нужно: health-фильтр продолжает вычищать мертвые прокси, так что выдача восстанавливается сама. |
| Источник вернул HTTP 200, но контент не парсится (`parse_error`: анти-бот-страницы, заглушки CDN) | `200` + последний хороший снимок, если он есть, иначе пустой валидный конф; заголовок `X-Fumox-Warning: parse-error`                                                                                                                     |
| Все прокси профиля в карантине/удалены (на `/src` — все прокси источника)                            | `200` + валидный **пустой** конф + заголовок `X-Fumox-Warning: all-proxies-quarantined`                                                                                                                                                  |
| Формат вывода не умеет выразить часть записей (протокол без аналога в этом формате)                  | `200` + те записи, которые формат выразить может + заголовок `X-Fumox-Warning: incompatible-entries-skipped` и число пропущенных в `X-Fumox-Skipped`                                                                               |
| Источник сломан окончательно (`http_client`: 400/403/404/410)                                     | Код ответа источника передается как есть; не кэшируется                                                                                                                                                                                  |
| Профиль не существует / отключен                                                                  | `404`                                                                                                                                                                                                                                    |
| Слишком много запросов с одного IP (лимит или исчерпанное окно неудачных попыток)                 | `429 Too Many Requests`, сбавьте темп                                                                                                                                                                                                    |
| Сломан сам Fumox (БД лежит, конфиг испорчен)                                                      | `500`                                                                                                                                                                                                                                    |

Прокси в состояниях `quarantine` и `removed` в выдаче не появляются никогда.
Прокси со статусом `unknown` (еще не проверены или непроверяемые tuic/mieru)
**включаются** в выдачу `/sub`: лучше отдать клиенту возможно-рабочий узел,
чем выбросить заведомо хорошие. `/src` и обе ссылки экспорта отдают только
живые уровни (`alive` и `ready`), поэтому `unknown` там не появляется.

#### Что отвечает какой эндпоинт

Класс ошибки последней загрузки источника решает, каким будет ответ, и оба
публичных эндпоинта судят его одинаково. Различается область: на `/sub`
класс **любого** источника-члена говорит за весь профиль, на `/src` — только
класс самого источника.

| Класс ошибки источника                                | `/sub/{profile}`                                                                                                               | `/src/{source}`                                                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `network`, `http_server` (upstream временно недоступен) | `200` + сохраненный снимок, `X-Fumox-Stale: true`                                                                             | `200` + сохраненный снимок, `X-Fumox-Stale: true`                                                       |
| `storage` (фид прочитан, запись отклонена базой)       | `200` + сохраненный снимок, `X-Fumox-Stale: true`                                                                             | `200` + сохраненный снимок, `X-Fumox-Stale: true`                                                       |
| `parse_error` (HTTP 200, контент не парсится)           | `200` + последний хороший снимок, а если его нет — пустой валидный конф; `X-Fumox-Warning: parse-error`                         | то же                                                                                                   |
| `http_client` (400/403/404/410)                         | код ответа источника из последней загрузки (`502`, если загрузка не записала код), не кэшируется; короткое замыкание **всего профиля** | код ответа источника из последней загрузки (`502`, если загрузка не записала код), не кэшируется           |
| все прокси в карантине/удалены                          | `200` + валидный пустой конф, `X-Fumox-Warning: all-proxies-quarantined`                                                          | `200` + валидный пустой конф, `X-Fumox-Warning: all-proxies-quarantined` (по прокси самого источника)    |
| формат вывода не умеет выразить запись                  | `200` + вывод, `X-Fumox-Warning: incompatible-entries-skipped`, `X-Fumox-Skipped: N`                                            | то же                                                                                                   |

Две разницы между эндпоинтами не зависят от класса ошибки. `/sub` отдает
прокси всех состояний, включая `unknown` (еще не проверенные); `/src`
отдает только живые уровни `alive` и `ready`. А ответы, которые вообще
не про источник — `404` на несуществующий или отключенный профиль/источник,
`403` на отсутствующий токен доступа, `429` на лимит частоты, `500` на
сломанный Fumox, — одинаковы на обоих.

## 7. Админ-панель

Админ-панель это серверный веб-интерфейс (askama + HTMX; каждая страница
работает даже с выключенным JavaScript). Она слушает **отдельный** сокет, по
умолчанию `127.0.0.1:8081`, физически отделенный от публичных эндпоинтов.

### Вход

Введите значение `[admin].token` на экране входа. Успешный вход ставит
подписанную (HMAC) HttpOnly-cookie сессии, действующую по умолчанию 7 дней
(`session_ttl_hours`). Смена токена в конфиге аннулирует все существующие
сессии. **Пустой токен** (или `enabled = false`) полностью отключает панель:
все маршруты `/admin/*` отвечают 404.

Встроенная защита: CSRF-токены в каждой форме, rate-limit по IP
(`120/min` общий, `5/min` на форму входа), безопасные заголовки ответов
(`X-Frame-Options: DENY`, `Content-Security-Policy`, `nosniff`,
`Referrer-Policy: same-origin`) и маскирование секретов на всех экранах.

Политика безопасности содержимого разрешает скрипты только с собственного
origin панели (`script-src 'self'`): панель отдает свой скрипт отдельным
файлом (`/admin/static/app.js`), и все обработчики делегированы оттуда,
поэтому внутри панели не выполняется ни встроенный скрипт, ни встроенный
обработчик события. Встроенные стили по-прежнему разрешены: в шаблонах
есть блок `<noscript>` и несколько атрибутов стиля.

Секрет маскируется везде, где панель его показывает. Креденшелы прокси
показываются как `user:sec…••••`, пароль в его прокси-строке маскируется так
же, а значение параметра, несущего креденшел (`password`, `api_key`,
`token`), показывается как `[redacted]`. Карточка говорит, что значение —
секрет, и в журнал оно не попадает.

Секрет внутри URL обрабатывается так же: источник, в адресе которого есть
пароль (`https://user:pass@host/sub`) или секретное значение в query
(`?token=…`), показывает его замаскированным в списке, на карточке и в форме
правки, а в сохраненном адресе он остается — загрузчику пароль нужен, и
сохранение формы без правки поля его сохраняет. Маска возвращается под тот
же ключ, который она заменила, поэтому источник, у которого токен лежит в
переименованном параметре, сохраняет свой токен. Токен доступа профиля
хранится в виде хэша, поэтому панель не может его показать: ссылка на
подписку несет только путь, а токен, который задал оператор, он добавляет
сам. Поле токена — это поле пароля, которое никогда
не показывает сохраненное значение, и панель отказывает в токене короче
16 символов.

### Время и часовые пояса

Все метки времени в панели (журнал загрузок, история проверок, жизненный
цикл прокси, очередь карантина) отображаются в **часовом поясе браузера**,
в формате, соответствующем языку интерфейса. Наведите курсор на метку, чтобы
увидеть исходный момент UTC и название зоны. Без JavaScript остается текст
UTC (`YYYY-MM-DD HH:MM:SS`). Хранимые данные, экспорт и серверные логи
всегда остаются в UTC.

### Клавиатура и программы чтения с экрана

Панель сделана так, чтобы ею можно было пользоваться без мыши и чтобы она
сообщала программе чтения с экрана, что делает:

- каждая страница работает и при выключенном JavaScript; скрипт, который
  подгружается при его наличии, добавляет только живые обновления и
  локальные удобства;
- форма, которую сервер отклонил, показывает сообщение **на том поле,
  которому оно принадлежит**: сообщение стоит под элементом управления, сам
  элемент на него ссылается (`aria-describedby`), помечен как невалидный
  (`aria-invalid`), а сообщение объявляется (`role="alert"`);
- редактор настроек разбит на три таба. Отклоненное сохранение открывает
  панель с первой ошибкой, а каждая панель с ошибкой помечена красным `!`
  в полосе табов, так что сломанная панель не остается незаметно неверной;
- диалог подтверждения ставит фокус на кнопку **отмены**, а не на кнопку,
  которая удаляет строки;
- переключатели (вкл/выкл) и живые бейджи объявляют новое состояние, а
  контейнеры, которые несут объявления, не пересоздаются при каждом
  обновлении, так что программа чтения с экрана не получает заново всю
  таблицу при каждом опросе;
- кнопки, которые требуют второго взгляда (разрушительное действие, пресет,
  который заменяет текущие правила), говорят в подписи или в том
  подтверждении, которое запрашивают.

### Удаление источника

Удаление источника разрывает и связь с накормленными им прокси: они теряют
ссылку на источник, а проход, который идет следом, трогает **только** прокси
этого источника — прокси, которые кормит другой источник, сохраняют свои
ссылки и свой статус.

Что проход делает с отключенными прокси, зависит от `[ingest].drop_gate`:

- `false` (мягкая политика): ничего не выводится из строя. Прокси `ready`
  проверен туннелем, а `unknown` еще не получил первого вердикта; probe —
  единственный источник истины о жизненном цикле проверенного прокси, а
  приоритетная очередь — единственный источник истины о непроверенном.
  Записи остаются на месте, просто без источника.
- `true` (строгая политика): каждый сирота этого источника помечается
  `removed`.

Если сам проход не удался, источник все равно удаляется, а панель сообщает
об этом в предупреждающем тосте: прокси, которые не удалось пометить,
перечислены в логе.

### Импорт и экспорт

*Экспорт* скачивает все источники и профили (с составом профилей, заголовками
и токенами доступа) в виде версионированного JSON-файла. Токен доступа
профиля выгружается **в виде своего хэша**, так что в файле никогда нет
рабочего секрета; импорт сохраняет тот же хэш, и эндпоинт остаётся рабочим
для клиентов, которые уже знают токен. *Импорт* воссоздает
их с семантикой **«только создание новых»**:

- импортируемые объекты всегда получают новые id; существующие записи никогда
  не перезаписываются;
- состав профилей пересчитывается на новые id источников;
- совпадение slug → объект создается без slug (сообщается как предупреждение);
- ссылка на источник, отсутствующий в файле → исключается из состава
  (предупреждение);
- одна ссылка у двух *строк источников* → отказ (ссылка связывает строки
  между собой, и по файлу не видно, какую из них имел в виду состав
  профиля);
- ссылка, повторенная дважды в списке источников одного *профиля* →
  остается одна (первая позиция);
- URL, который сейчас не разрешается → импортируется с предупреждением
  (адрес проверяется заново при каждой загрузке, поэтому недоступный
  на минуту хост не повод отказать в файле); URL, который разрешается в
  приватный адрес → отказ, если только в развертывании не разрешены
  приватные адреса;
- валидация все-или-ничего: любой невалидный объект прерывает весь импорт
  (`422` со списком проблем, ничего не записывается);
- сама запись идет одной транзакцией: сбой на полпути оставляет базу ровно
  такой, какой она была.

Импорт принимает не больше **500 строк в каждой таблице** (источники,
профили) и документ не больше **256 КиБ**. Оба числа показаны рядом с полем
загрузки, и кнопка экспорта несет те же числа рядом с собой. Документ больше
предела отклоняется с `422` до разбора, и так же отклоняется тело, которое
не является JSON или в котором нет поля `version`.

Успешный импорт отвечает переадресацией обратно на этот экран и всплывающим
сообщением с итогами: сколько источников и профилей создано и сколько
предупреждений дал файл. Сами предупреждения — в журнале, по строке на
каждое.

Экспорт называет и свои пределы. Развертывание с числом источников или
профилей больше 500 либо с конфигурацией, которая сериализуется длиннее
256 КиБ, дает файл, который экран импорта не примет; такой файл несет поле
`import_limit` с именем превышенного предела, сервер пишет об этом
предупреждение, а сами пределы показаны рядом с кнопкой экспорта. Сам файл
остается полным: отказывает импорт.

На этом же экране **две публичные ссылки** сведены в одну таблицу вместе
с текущим числом прокси. Обе ссылки делят общий случайный токен:

- `GET /export/alive/{token}`: все текущие живые прокси в формате
  `url_list`. Заголовок в блоке метаданных: `export/alive`, интервал
  обновления `1` час.
- `GET /export/ready/{token}`: только ярус `ready` (прокси, успешно
  прошедшие обе T1 и T2 проверки). Тот же формат, заголовок `export/ready`.

Обе ссылки отдают снимок состояния, а не живое представление, и
ограничены дважды:

- **Не больше 50 000 строк в теле**, это поставляемое значение
  `[server].export_max_rows`. В отличие от `/sub` и `/src`, у этих двух
  ссычек нет своего лимита на источник или профиль, поэтому очень большой
  пул превращал бы одну загрузку в неограниченное чтение и неограниченный
  файл. Если ярус больше, поднимите ключ. Обрезка берет самые старые строки
  (наименьшие id), а заголовок `nodes count` сообщает, сколько строк в теле
  на самом деле. Тело, уперевшееся в лимит, сообщает об этом само: в блок
  метаданных добавляется строка `# truncated: showing 50000 of 81234 — raise
  [server].export_max_rows` с примененным лимитом и ключом, который его
  поднимает (сам ярус назван заголовком `export/alive` или `export/ready`
  над ней), а сервер пишет одно предупреждение на ярус за окно в 30 секунд,
  чтобы молчаливый лимит не прошел незамеченным. Те же два факта несут и
  заголовки ответа: `X-Fumox-Export-Total` называет размер яруса, а
  `X-Fumox-Export-Truncated: true` помечает тело, обрезанное лимитом, так
  что клиент с одними только заголовками (загрузка, прокси на пути) все
  равно отличает полный список от обрезанного. Живые
  счетчики рядом со ссылками **не** ограничены: они показывают реальный
  размер яруса, по ним и видно, что выгрузка меньше пула.
- **Кэш на 30 секунд.** Пачка загрузок внутри одного окна отдается из одного
  и того же тела, так что обычный случай стоит одного формирования, а не
  одного на запрос. Обновление тела тоже схлопывается: когда окно истекло,
  формирует только первый запрос, а остальные ждут его свежее тело, вместо
  того чтобы каждая формировала ярус заново. Плата (свежесть):
  умерший прокси может еще попасть в тело в течение 30 секунд
  после изменения. Выгрузка по определению снимок, и тихо устаревший файл
  хуже чуть более медленного запроса: просроченное тело формируется заново,
  устаревшее не отдается.

Ярусы не пересекаются, поэтому прокси в состоянии `ready` попадает только
в `/export/ready` и никогда в `/export/alive`.

«Скачать url_list» сохраняет ответ файлом, а «Перевыпустить ссылку»
меняет токен, если ссылка утекла (старая ссылка перестает работать сразу,
обе ссылки ротируются вместе). Ротация спрашивает подтверждения на
отдельной странице, поэтому промах по кнопке не обрывает ссылки, которыми
уже пользуются клиенты. Токен хранится в памяти процесса и общий
для панели и публичного слушателя, поэтому загрузка не читает базу;
сохраненная копия — запасной вариант, который переживает перезапуск.

Если токен Capability или счетчики прочитать не удалось, блок с двумя
ссылками скрывается, а причина уходит в журнал, вместо того чтобы весь экран
превращался в страницу ошибки. Форма импорта остается рабочей в любом случае.

Форма импорта принимает JSON как вставкой в текстовое поле, так и через
выбор файла: выбранный файл загружается в то же текстовое поле; вставка
вручную работает и без JavaScript.

### Языки и темы

Интерфейс многоязычный: русский (по умолчанию) и английский вшиты в бинарник;
язык выбирается на экране входа и запоминается в cookie `fumox_lang`. Чтобы
добавить язык, скопируйте любой файл из `locales/`, переведите значения,
сохраните как `locales/<код>.toml` (плоские пары
`"domain.key" = "текст"`) и перезапустите сервер, пересборка не нужна. Файлы
на диске перекрывают вшитые каталоги.

Тема день/ночь переключается на экране входа или в топбаре (cookie
`fumox_theme`); выбор работает без JavaScript.

## 8. Справочник по конфигурации

### Как разрешается конфигурация

Три слоя, побеждает более поздний:

1. **Встроенные дефолты**: они есть у каждого ключа; Fumox работает вообще
   без файла конфигурации.
2. **TOML-файл**: путь выбирается по приоритету: флаг `--config / -c` →
   переменная окружения `FUMOX_CONFIG` → `config/app.toml` от текущей
   директории. Файл может быть частичным: только нужные секции. Файл,
   заданный флагом или переменной, обязан существовать (опечатка в пути дает
   громкую ошибку старта, а не тихий отход к дефолтам); отсутствует
   только дефолтный путь, приложение работает на встроенных дефолтах.
3. **Переменные окружения**: `FUMOX_SECTION__KEY`, где двойное подчеркивание
   отделяет секцию от ключа:

   ```bash
   FUMOX_CONFIG=/etc/fumox/app.toml  # путь к TOML-файлу (если нет --config)
   FUMOX_ADMIN__TOKEN=secret          # [admin] token
   FUMOX_DATABASE__PATH=/data/f.db    # [database] path
   FUMOX_MEOW__API_ADDR=meow:9090     # [meow] api_addr
   ```

   Окружение перекрывает файл на каждом ключе: `String`, `bool`,
   целые числа и `SocketAddr` принимают значение из env как есть. Для
   `Vec<String>` нужно передать JSON-массив
   (`FUMOX_SERVER__TRUST_PROXY_IPS='["10.0.0.0/8"]'`), а не
   строку через запятую, кроме полей с кастомным десериализатором
   (например, `[meow].test_url`, который принимает оба варианта).

Аннотированный эталонный файл: [`config/app.toml`](./config/app.toml) в
репозитории. В таблице ниже встроенные дефолты из
`crates/fumox-core/src/config.rs`; в поставляемом `config/app.toml` для части
ключей стоят другие значения.

### Куда указывают относительные пути

Любой относительный путь в конфигурации разрешается от **текущей рабочей
директории процесса** — и никогда от директории, в которой случайно
оказался файл конфигурации:

| Путь | Дефолт | Разрешается от |
| ---- | ------ | -------------- |
| сам файл конфигурации (`--config`, `FUMOX_CONFIG`, дефолтное место) | `config/app.toml` | рабочей директории |
| `[database].path` | `fumox.db` | рабочей директории |
| `[geo].db_dir` | `config` | рабочей директории |
| `[admin].locales_dir` | `locales` | рабочей директории |
| `[meow].config_path` | `config/meow.yaml` | рабочей директории |

Поэтому менеджеру служб нужно сказать, где работает процесс: юнит без
`WorkingDirectory` стартует в `/`, и все относительные пути конфигурации
указывают на `/`, а не на нужный каталог. Выходов два, и первый
предпочтительнее:

- **абсолютные пути в конфиге** — `[database].path =
  "/var/lib/fumox/fumox.db"`, `[geo].db_dir = "/var/lib/fumox/geo"`,
  `[admin].locales_dir = "/etc/fumox/locales"`: развертывание не зависит от
  того, откуда процесс запустили;
- **зафиксированная рабочая директория** — `WorkingDirectory=/opt/fumox` в
  юните, а относительные пути пишутся относительно нее.

| `export_max_rows`      | `50000`          | Потолок строк в одном теле `/export/alive/{token}` / `/export/ready/{token}`, заданный как `LIMIT` в запросе за ними. Обрезка берет наименьшие id, а заголовок `nodes count` сообщает, сколько строк в теле на самом деле; счетчики яруса в админке не урезаны, поэтому обрезанная выгрузка видна как меньшая яруса; заголовки ответа называют саму обрезку (`X-Fumox-Export-Truncated`) и размер яруса (`X-Fumox-Export-Total`). `0` не значит «без ограничения»: значение поднимается вверх до 1 строки (ноль или минус в `LIMIT` SQLite прочитала бы как бесконечность), поэтому тело при `0` отдает один узел. ### `[meow]` – интеграция с meow-rs (T2)

| Ключ                   | По умолчанию                                                                                          | Значение                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api_addr`             | `"127.0.0.1:9090"`                                                                                    | Адрес REST API meow-rs (его external-controller)                                                                                                                                                                                                                                                                                               |
| `config_path`          | `"config/meow.yaml"`                                                                                  | Куда probe пишет сгенерированный Clash-конфиг. **Путь должен быть читаем самим meow-rs** (в Docker: общий том)                                                                                                                                                                                                                                 |
| `test_url`             | `["https://www.gstatic.com/generate_204"]`                                                                              | URL(ы), запрашиваемые через прокси для замеров задержки: один адрес, TOML-массив или строка через запятую. Каждый адрес должен быть абсолютным `http(s)`-URL (другая схема и адрес без хоста отвергаются при загрузке конфига). Probe выбирает один адрес на цикл, и все проверки цикла бьют по нему, поэтому недоступный адрес больше не дает одному прокси разные вердикты подряд; когда провалился весь батч, прокси получают отметку "не проверен", а не запись в лестницу отказов. Дефолт — один HTTPS-эндпоинт: семь адресов одного вендора убрали, потому что в регионе, где этот вендор заблокирован, падали сразу все прокси. Адреса проверки iOS/Apple (`captive.apple.com/...`) отвечают 200, а не 204: использовать можно, но только если допустим не-204 ответ |
| `timeout_secs`         | `10`                                                                                                  | Таймаут одной проверки                                                                                                                                                                                                                                                                                                                         |
| `backoff_initial_secs` | `60`                                                                                                  | Начальная задержка (backoff) T2, когда meow-rs недоступен (удваивается с каждым подряд идущим провалом)                                                                                                                                                                                                                                        |
| `backoff_max_secs`     | `900`                                                                                                 | Потолок backoff T2 (15 мин), мертвый meow-rs никогда не принимается за мертвые прокси                                                                                                                                                                                                                                                          |
| `ipv6`                 | `false`                                                                                                 | Попадает в генерируемый конфиг meow как ключ `ipv6`. meow-rs **0.22.0 сделал ключ действующим от начала до конца**: при `false` AAAA не опрашиваются и direct-исходящий отвечает только IPv4, тогда как 0.21.x резолвил обе семьи независимо от ключа. Через резолвер проходит только хост *test_url* (серверы прокси пинятся генератором в проверенный IP-литерал), так что менять стоит лишь при IPv6-only исходящем трафике или test URL только по AAAA. Дефолт совпадает с meow-rs |

| Ключ                 | По умолчанию | Значение                        |
| -------------------- | ------------ | ------------------------------- |
| `probe_results_days` | `14`         | Хранить историю проверок N дней |

| `removed_proxies_days` | `0`        | Стирать прокси, удалённые более N дней назад; `0` = выключено |

Оба процесса читают один файл, поэтому ключ свой у каждого. Уровень: один из

| Ключ     | По умолчанию | Значение                                                                                       |
| -------- | ------------ | ---------------------------------------------------------------------------------------------- |
| `server` | `info`       | Уровень консольных логов `fumox-server`                                                        |
| `probe`  | `info`       | Уровень консольных логов `fumox-probe`; `warn` убирает строку «probe cycle done» каждого цикла |

## 9. Конвейер обработки (pipeline)

Pipeline это версионированный JSON-документ, который хранится на источнике
и/или профиле (pipeline профиля перекрывает совпадающие секции источника).
Все секции необязательны: `{}` (или отсутствие pipeline) означает «пропустить
как есть и дедуплицировать по фингерпринту». Поле `"version": 1` обязательно.

```json
{
  "version": 1,
  "filter": {
    "protocols": ["vless", "trojan"],
    "exclude_protocols": ["naive"],
    "asns": ["24940", "AS13335"],
    "exclude_asns": ["9009"],
    "forbid_insecure": true
  },
  "drop": [
    { "match": "free|trial", "flags": "i" },
    { "match": "\\.cn$", "target": "host" },
    { "match": "^80$", "target": "port" },
    { "match": "^chrome$", "target": "param:fp" }
  ],
  "rename": [
    { "match": "^(.*?)\\s*\\|", "replace": "$1", "flags": "i" },
    { "match": "^chrome$", "replace": "firefox", "target": "param:fp" },
    { "match": "server1\\.tr$", "replace": "invalid.tr", "target": "host" },
    { "match": "^123$", "replace": "456", "target": "port" }
  ],
  "geo": { "enabled": true, "template": "{flag} {country} · {name}" },
  "health": { "exclude_statuses": ["quarantine", "removed"] },
  "dedup": { "by": "fingerprint" },
  "sort": { "by": "source", "desc": false },
  "limit": { "count": 100 }
}
```

| Секция   | Что делает                                                                          | Поля и дефолты                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `filter` | Оставить/отбросить протоколы и номера AS; выбрасывать прокси с разрешённым insecure | `protocols` / `exclude_protocols`: списки или null (= все); `asns` / `exclude_asns`: списки номеров AS или null, сверка с сохранённым `geo_asn`; если у строки его нет, номер определяется при отдаче, но только когда в игре действительно есть ASN-правило (ASN-фильтр или ASN-правило в `drop`) — резолв закеширован, и шаг geo-enrich спрашивает тот же хост через пару строк, — поэтому без номера остаётся только хост, который действительно не резолвится: allowlist его отбрасывает, exclude-список оставляет (работают написания и `"24940"`, и `"AS24940"`). Пайплайн без ASN-правила при отдаче не резолвит ничего: номер добирают инжест и гео-бэкфилл; `forbid_insecure`: по умолчанию `true`, выбрасывает прокси с truthy-переключателем `insecure`/`allowInsecure`/`skip-cert-verify`/`allow_insecure` (старое имя `normalize_params` также принимается). Проверка insecure идёт после правил rename, поэтому судит те параметры, на которых пайплайн остановился: rename, переписавший небезопасный переключатель, будет пойман |
| `drop`   | Отбросить подходящие прокси целиком (не записываются в базу)                        | `match` (regex), `flags`, `target` (опц.: `name` дефолт, `host`, `port`, `param:KEY`, `asn`); правило `asn` не несет `match`/`flags` и вместо них требует непустой список `asns` в самом правиле (работают написания и `"24940"`, и `"AS24940"`), сверяемый с определённым номером AS прокси; правила ИЛИ-ятся; по умолчанию `[]` |
| `rename` | Переписывание по regex, правила применяются по порядку                              | `match` (regex), `replace`, `flags` (например, `"i"`), `target` (опц.: `name` дефолт, `host`, `port`, `param:KEY`); по умолчанию `[]`                                                                                                                                                                                                                                                                                                                   |
| `geo`    | Переписать отображаемые имена с гео-данными                                         | `enabled` (по умолчанию `true`), `template` (по умолчанию `"{flag} {country} · {name}"`; плейсхолдеры в [разделе 11](#11-гео-обогащение))                                                                                                                                                                                                                                                                                                                |
| `health` | Исключить прокси по статусу                                                         | `exclude_statuses`, по умолчанию `["quarantine", "removed"]`; принимаются все пять статусов: `unknown`, `alive`, `ready`, `quarantine`, `removed`                                             |
| `dedup`  | Дедупликация                                                                        | `by`: в v1 только `"fingerprint"`                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `sort`   | Порядок выдачи                                                                      | `by`: `source` \| `name` \| `country` \| `latency` (NULL-латентности в конец); `desc`: по умолчанию `false`                                                                                                                                                                                                                                                                                                                                              |
| `limit`  | Ограничить размер выдачи                                                            | `count`: целое ≥ 1, у источника не больше этого числа его собственных прокси до слияния с остальными источниками профиля; у профиля: не больше этого числа прокси итогового (после дедупликации и сортировки) списка (его верх). Ограничение источника не ограничивает профиль из нескольких источников: такой профиль отдаёт верх каждого источника в пределах этого числа, то есть всего больше, чем `count`; `null`/отсутствует = без ограничения  |

Валидация строгая: неизвестные ключи, некомпилируемый regex или неверное
значение enum отклоняются с ошибкой у поля в форме админки, ничего не
сохраняется. Эта строгость осознанна: будущая схема v2 сможет добавлять поля
без двусмысленности старых конфигов.

В админке пайплайн правится через форму. Каждую секцию можно оставить на
встроенном дефолте, задать явным значением или убрать; так же работают
переключатели внутри секции (проверка insecure, гео-переписывание):
нетронутый переключатель сохраняет дефолт, снятый — присылает своё «off».
Текст правила — regex, замена, флаги, список AS — читается дословно, вместе с
пробелами: паттерн с пробелом в начале или в конце это другой паттерн, и
обрезка молча изменила бы смысл правила.

Форма — не единственный вход. Пайплайн, который форма не может выразить
(секция, неизвестная билдеру, правило, которое он не выражает), правится как
raw JSON, а не переписывается во что-то другое. Значение, которого форма не
понимает, — несуществующий ключ сортировки или нечисловой лимит — остается в
документе и попадает в ошибку у того поля, откуда оно пришло, так что панель
называет ошибку, а не молча откатывается к дефолту.

Необязательное поле `target` правила выбирает, что переписывает его regex;
отображаемое имя лишь его дефолт: `name` (в JSON опускается) дает классическое
переименование; `host` и `port` переписывают адрес прокси, а `param:KEY` затрагивает
первый параметр с этим ключом (без учета регистра: фиды мешают
`headerType` и `headertype`). Значения параметров матчятся и записываются в
сыром percent-encoded виде, ровно как в URI, поэтому `path=%2Fws`
переписывается через его кодированное написание. Результаты `host`/`port`
защищаются на отдаче: пустой host, URI-разделители в host или порт вне
0–65535 пропускаются, оригинал сохраняется, одно сломанное правило не
испортит все строки подписки. Пропуски считаются по правилам и отчитываются
одной строкой WARN на правило — индекс правила, его target, число пропущенных
записей и один пример значения, — а не строкой на каждый прокси, так что фида
с тысячей сломанных записей не забьёт лог. Учтите: переписывание
`host`/`port`/`param` меняет фингерпринт прокси на отдаче: два узла,
переписанные в один адрес, склеятся на шаге дедупликации (она идет после
rename, побеждает первое вхождение).

Секция `drop` работает наоборот: вместо переписывания подходящий прокси
выбрасывается целиком: он не появляется в подписке, потому что вообще не
записывается в базу. Правила используют те же селекторы, что rename
(`match`, `flags`, `target`; без `replace`, строгая схема его отвергает),
и ИЛИ-ятся: одного срабатывания достаточно, чтобы отбросить прокси.
Исключение из regex-селекторов — target `asn`: он не несет `match`/`flags`
(строгая схема их отвергает) и вместо них требует непустой список `asns`
в самом правиле (работают написания и `"24940"`, и `"AS24940"`),
сверяемый с определённым номером AS прокси; прокси без определённого ASN
под такое правило не попадает. Применяются дважды, всегда до `rename`, обе стороны видят исходные
значения: при инжесте это пайплайн самого источника (подходящий прокси не
записывается, не проходит гео-резолв и не ставится в очередь проверок;
поврежденный конфиг фейлится как parse-ошибка, а если под правила попало
все, фетч журналируется как parse-ошибка, база не тронута), а на отдаче
это действующий пайплайн (поэтому секция `drop` в профиле тоже работает, а
правило, добавленное задним числом, сразу прячет уже записанные строки).
Записанные до появления правила прокси уходят естественным lifecycle:
следующий refresh источника не подтверждает их связь заново, они отвязываются
и без другого источника помечаются `removed` машиной состояний probe,
жестких удалений нет. Прокси, отброшенный одним источником, но публикуемый
другим, остается в базе. Dry-run в админке показывает, сколько прокси
отбросили фильтры источника: правило можно настроить до первого реального
фетча.

Конвейер выполняется в фиксированном порядке:
**parse → filter → drop → rename → geo → health-filter → merge + dedup → sort → encode.**

Один фильтр срабатывает дважды: проверка insecure (`filter.forbid_insecure`)
идёт вместе с остальными фильтрами и ещё раз после правил rename, потому что
rename может внести небезопасный переключатель — второй проход видит те
параметры, на которых пайплайн остановился.

## 10. Проверка живучести и жизненный цикл прокси

Демон `fumox-probe` работает в бесконечном цикле (по умолчанию каждые 60 с);
каждый цикл состоит из четырех проходов:

1. **Карантинные сроки**: вторые шансы и ступени повторных проверок, чей момент
   наступил (карантинный hysteria2 перепроверяется через T2-туннель, см. ниже);
2. **Приоритетная очередь**: только что добавленные прокси, которые сервер
   поставил в очередь при обновлении источника (до `[ingest].refresh_check_limit`
   на обновление); очередь разбирается начиная с самых свежих, взятые записи удаляются
   из очереди до проверки;
3. **T1**: случайная выборка прямых проверок TCP-соединением (плюс
   TLS-рукопожатие, если протокол подразумевает TLS) по прокси
   `unknown`/`alive`;
4. **T2**: настоящие туннельные проверки через meow-rs: probe пишет
   Clash-конфиг с батчем, горячо перезагружает meow-rs через `PUT /configs`,
   затем меряет задержку через `GET /proxies/{name}/delay` на одном адресе,
   выбранном из `[meow].test_url` (все проверки цикла идут по нему же). В выборку попадают `alive`- и `ready`-прокси, а также еще не
   проверенные `unknown`-hysteria2, которым T1 ничего не может доказать (см. ниже).
   Порядок выборки определяется давностью, а не случайностью: первыми идут прокси, у
   которых туннельных проверок не было вовсе, затем те, чья последняя
   проверка старее остальных; так в большом пуле ни один прокси не
   задерживается без туннельной верификации, пока его `alive` держится
   на одном лишь TCP-коннекте.

Приоритетная очередь дает новым прокси первую проверку в пределах одного цикла
после обновления источника, без нее при больших объемах ожидания случайной
выборки растягиваются на часы и дни. Непроверяемые схемы в очередь не
попадают вовсе (их все равно не проверить), а прокси, ставший проверенным
через случайную выборку, из очереди просто выпадает.

| Уровень          | Что доказывает                                              | Применим к                                  |
| ---------------- | ----------------------------------------------------------- | ------------------------------------------- |
| **T1** (TCP/TLS) | Сервер доступен по `host:port`                              | vless, vmess, trojan, ss, socks5, naive     |
| **T2** (туннель) | Прокси *действительно работает*: креды валидны, трафик идет | vless, vmess, trojan, ss, hysteria2, socks5, snell, anytls |

QUIC-протоколы (hysteria2, tuic) пропускают T1: TCP-коннект к UDP-порту
ничего не доказывает. **hysteria2** от этого не страдает: свежий
`unknown`-hysteria2 сразу попадает в T2-выборку и дальше живет обычной
машиной состояний (счетчик неудач общий с T1). T2-путь не закрывается и в
карантине: карантинный hysteria2 оживляется настоящей туннельной проверкой
через meow-rs, а не TCP-коннектом, который пройти не может в принципе:
успех возвращает строку в ярус `ready` с чистым листом, провал туннеля
двигает ту же лестницу повторов, что и у остальных схем. **tuic и mieru непроверяемы**
вовсе (meow-rs их не поддерживает): они навсегда остаются в статусе
`unknown`, всегда проходят health-фильтры и помечаются бейджем «unprobeable»
в админке. Исключить их из профиля можно фильтром `filter.protocols`.

### Машина состояний статусов

```mermaid
stateDiagram-v2
    [*] --> unknown : новый прокси появился в источнике
    unknown --> alive : успешна проверка T1
    unknown --> ready : успешна проверка T2
    alive --> ready : успешна проверка T2
    ready --> alive : проверка T2 не прошла
    unknown --> quarantine : fail_limit неудач подряд
    alive --> quarantine : fail_limit неудач подряд
    ready --> quarantine : fail_limit неудач подряд
    quarantine --> alive : второй шанс или ступень лестницы успешны
    quarantine --> ready : туннельное оживление hysteria2 успешно
    quarantine --> removed : провалены второй шанс и все ступени лестницы
    note right of unknown
        hysteria2 пропускает T1
        и сразу попадает в T2-выборку
    end note
    note right of quarantine
        карантинный hysteria2 оживает
        через T2-туннельную проверку
    end note
```

Правила простым языком:

- **Успех возвращает прокси в строй, но вердикт T2 главнее.** Любая успешная
  проверка очищает расписания: успех T1 оставляет прокси в `alive`
  (`ready`-строка остается `ready`), успех T2 переводит его в `ready`. Успех T2
  и карантинное оживление обнуляют и счетчик неудач; успех T1 обнуляет его,
  только если последняя неудача была T1. Прокси с мертвым туннелем (это видит
  только T2) продолжает накапливать неудачи до `fail_limit`, даже если каждый
  T1 проходит.
- **Карантин.** `fail_limit` (по умолчанию 3) неудач подряд переводят
  `unknown`-, `alive`- или `ready`-прокси в `quarantine`. Он немедленно
  исчезает из подписок.
- **Второй шанс.** В случайный момент окна **[12ч, 16ч)** после карантина
  (`quarantined_at + second_chance_min_hours + U(0..second_chance_spread_hours)`,
  UTC, разыгрывается один раз и сохраняется) прокси проверяется заново.
  Успех → обратно в `alive`. Для всех схем, кроме hysteria2, второй шанс и
  ступени лестницы это T1-проверки, и карантинный прокси в T2-выборку больше
  не попадает. Карантинный hysteria2 — единственное исключение: его второй
  шанс и ступени лестницы идут как T2-туннельные проверки через meow-rs
  (TCP-коннект к QUIC-порту пройти не может), и успешная туннельная проверка
  возвращает его сразу в `ready`.
- **Лестница повторных проверок.** После провала второго шанса прокси проходит
  лестницу из `[probe].recheck_delays_secs` (по умолчанию 15 мин → 30 мин →
  1 ч): провал ступени N назначает ступень N+1 через N-й элемент массива;
  провал последней ступени → `removed`. Любой успех → `alive`; у карантинного
hysteria2 успех приносит T2-туннельное оживление и сажает его в `ready`. Длина лестницы
  произвольная (до 16 ступеней, каждая не больше 30 дней); пустой массив
  удаляет прокси сразу после провала второго шанса. С дефолтами весь путь
  от карантина до removed занимает ~13 ч 45 мин – 17 ч 45 мин.
- **Removed это не удаление.** Удаленные прокси остаются в базе (кнопка
  *«Стереть удалённые»* в админке чистит их физически). `removed` это
  терминальный статус: если источник снова отдает такой прокси, его состояние
  **не** сбрасывается: reconciliation никогда не касается машины состояний
  (она под владением probe). Пути назад: *«Сбросить статус»* на карточке
  прокси либо *«Стереть удалённые»*, после которого следующая загрузка
  вставит прокси заново.
- **«Сбросить статус» сбрасывает только то, до чего дотянет probe.** Кнопка
  возвращает строку в чистый `unknown` и ставит ее в приоритетную очередь,
  то есть что-то делает она только для прокси, который probe действительно
  посмотрит. Для строки, до которой ни одна проверка не дотянется (не
  осталось связи ни с одним источником либо схема не проверяется (`tuic`,
  `mieru`)), панель прямо говорит об этом и оставляет статус как был, бейдж
  не меняется. Именно связь с источником ставит строку перед probe, а
  reconciliation снимает ее на следующем refresh, поэтому такой прокси нужно
  заново внести через источник (либо *«Стереть удалённые»* и дождаться
  следующей загрузки), а не нажимать кнопку еще раз.
- **Исчезновение из источника не убирает живой прокси (alive-linger).**
  Если refresh источника больше не видит прокси, линк сохраняется, пока
  строка находится в `alive`, `ready`, `unknown` или `quarantine`: прокси
  продолжает проходить цикл проверок и оставаться в подписках этого
  источника. Когда именно уходить, решает только probe. Исключение —
  источники с `drop`-правилами **при включенном** `[ingest].drop_gate = true`
  в конфиге (тогда правило, добавленное задним числом, убирает уже
  записанные строки на ближайшем refresh; при дефолтном `true` так и
  происходит, если ключ не выставлен в `false` явно, а до этого drop-правила
  отсекали только новые совпадения). Удаление источника в админке действует
  сразу: связи снимаются, лингера нет.

### Правка `config/app.toml` из панели

С обзора ведёт страница `/admin/settings/edit`, форма-редактор на основе
[`toml_edit`](https://crates.io/crates/toml_edit), которая пишет файл
на месте. Все комментарии, которые вы писали в `config/app.toml` (пары
RU/EN, баннеры, подсказки, каждая строка `#…`) переживают каждое
сохранение: редактор работает с распарсенным документом, а не
перегенерирует его. Секции сгруппированы по процессам-владельцам
(Server / Probe / Shared) через табы на `<input type="radio">` без
JavaScript.

Изменения **требуют перезапуска**: панель сохраняет файл, но server
и probe перечитывают его при старте, поэтому оба процесса нужно
перезапустить. Тост после сохранения об этом напоминает. Переменные
окружения `FUMOX_SECTION__KEY` по-прежнему перебивают значения файла
по существующему merge в figment, для разовых подстроек ENV остаётся
самым быстрым инструментом.

Форма показывает значения **файла**, а не работающей конфигурации:
панель пишет файл, значит видеть надо файл. Настройка, которую
перекрывает окружение (`FUMOX_SECTION__KEY`), рендерится только для
чтения, перечисляется над формой и в запись не попадает — слой
окружения сильнее файла, поэтому записанное здесь значение всё равно
не вступило бы в силу. Сбросьте переменную, чтобы поле снова стало
редактируемым. Сохранение, которое затронуло такую настройку, говорит
об этом в тосте, а не делает вид, что всё прошло; сохранение, которое
затронуло перекрытый окружением `[admin].token`, отмечается как ошибка:
панель продолжает работать под токеном окружения.

Смена `[admin].token` или переключение `[admin].secure_cookies` инвалидирует
все активные сессии на следующем запросе: панель читает новое значение на
старте, поэтому cookie, подписанные старым токеном, перестают проходить
проверку, поэтому залогиненные пользователи молча разлогинятся. Планируйте такие
правки на тихое окно и заранее предупредите тех, кто в админке. Смена токена
через панель завершает и остальные сессии — и только смена токена: обычное
сохранение вашу сессию не трогает.

Редактор узко заточен под безопасность:

- Если `config/app.toml` отсутствует, кнопка **Править** скрыта и
  вместо неё показывается **Создать из дефолтов**: копирует в этот путь
  эталонный конфиг из репозитория, чтобы server при следующем
  рестарте имел что парсить. Редактор сразу открывается на новом
  файле. Существующий файл кнопка не перезаписывает.
- Если существующий файл **не доступен на запись** (ФС только для
  чтения, родительского каталога нет, владелец не тот), редактор
  рендерится, но все контролы заблокированы, поверх висит красный
  баннер с причиной; тот же баннер показывается на обзоре.
- Валидация проходит за один проход при сохранении: некорректный `bind`,
  выход за диапазон, неизвестное значение enum, пустой обязательный
  список превращаются в красные сообщения у полей (`422`); пока не
  валидно всё, ничего не пишется. `bind` проверяется через
  `SocketAddr::from_str`, лестница recheck разбирается как `Vec<i64>`,
  лимиты как `<N>/<единица>`.
- Лимит частоты, у которого в форме приехала только половина пары
  (число без единицы или единица без числа), отклоняется с ошибкой у
  поля: недостающая половина берётся из файла для проверки, а запись
  не происходит.
- Чекбокс, которого браузер не прислал, свою настройку не трогает.
  Рядом с каждым чекбоксом форма отправляет скрытое `value="off"`, так
  что снятый чекбокс — это явное «off»; но поле, которое не пришло
  вовсе, — это не выбор оператора.
- Конфиг, который панель собирается записать, проверяется загрузчиком
  до попадания на диск. Файл, который бинарники не примут, поднимает
  их оба при следующем старте, поэтому запись отклоняется с причиной
  на странице, а файл на диске остаётся байт в байт прежним.
- Поле токена админки обычный input; пустая строка сохраняет
  текущий токен (используется для HMAC поверх cookie сессии), чтобы
  панель не выключила себя сама. Смена токена инвалидирует все
  активные сессии со следующего запроса.
- Легаси-поле `[geo].db` рендерится как disabled с подсказкой:
  оно остаётся только для совместимости парсинга и больше не
  влияет на резолвинг.

Если файл конфига прочитать не удалось (сломанный TOML, секция,
которую загрузчик не знает), редактор говорит об этом баннером и
показывает работающие значения — а это не значения файла: под баннером
те, что действуют сейчас, а не те, что лежат на диске.

Запись атомарна на пути с `rename`: редактор пишет в `<path>.tmp.<pid>` и
делает `rename` поверх оригинала, так что файл оказывается либо полностью
заменён, либо полностью нетронут. Два fallback-а пишут **сквозь исходный
файл** — ФС отказала в rename или временному файлу не удалось передать
владельца оригинала, — и этот путь обрезает файл перед записью: сбой в
середине оставляет конфиг обрезанным, и следующий старт читает сломанный файл.
Оба fallback-а пишут предупреждение в лог, поэтому строка `atomic rename
failed` (или `could not give the temporary file the original's owner`) — это
сигнал сделать резервную копию перед следующим сохранением.

Если meow-rs лежит, T2 не спамит его: probe увеличивает задержку экспоненциально
(60 с → удвоение → потолок 15 мин), статусы прокси не трогаются: мертвый
meow-rs никогда не принимается за мертвые прокси. T1 и сервер не страдают;
Fumox прекрасно работает без meow-rs, просто без туннельной верификации.

Все состояние жизненного цикла живет в SQLite, поэтому демон restart-safe:
перезапускайте его когда угодно, расписания возобновятся из базы.

### Тюнинг производительности probe

Когда пул карантина растёт быстрее, чем цикл его осушает, страница
`/admin/probe` показывает баннер с эвристикой и конкретными значениями
параметров, которые стоит изменить. За пропускную способность
отвечают три ручки:

| Ручка | Эффект | Когда крутить |
|-------|--------|--------------|
| `[probe].sample_size` | Сколько строк цикл берёт из очереди, до параллелизации. | Первая ручка, основной рычаг пропускной способности. |
| `[probe].concurrency` | Параллельных проверок *внутри* цикла. | Только когда один цикл перестаёт укладываться в `cycle_interval_secs`. |
| `[probe].cycle_interval_secs` | Как часто стартует новый цикл. | Уменьшать только после того, как `sample_size` уже большой. |

Баннер выводит все цикловые числа из одной модели:

```
retire_per_cycle = min(sample_size, due_count)
lane             = ceil(retire_per_cycle / concurrency)
                   × (connect_timeout_secs + tls_timeout_secs)
period           = max(cycle_interval_secs, lane)
drain_minutes    = ceil(quarantine_count / retire_per_cycle) × period / 60
```

`due_count`: сколько строк в карантине имеют `ladder_at` в прошлом.
Именно поэтому большая очередь сама по себе ещё не бэклог: строка,
попавшая в карантин минуту назад, станет доступна через 12–16 ч, цикл
не сможет её забрать, и никакая настройка на этой странице это не
изменит.

`lane` считает только полосу карантина, единственную, которая убирает
строки из очереди. Цикл дожидается ещё и полосы накопленных проверок,
выборки T1 и пачки T2, и оценка намеренно не претендует на их работу.
`period` берёт `max`, потому что тикер демона пропускает пропущенные
тики: полоса длиннее интервала сдвигает следующий старт на время работы.

Когда `retire_per_cycle` равен 0, обычно потому, что окно второй
попытки ещё не истекло, цикл не берёт ничего, и осушать нечего. Тогда
баннер сообщает, что цикл взял и сколько строк готово к проверке, вместо
цифры, которой у него нет. Выборка в 0 — не состояние, которое конфиг
принимает (`probe.sample_size` начинается с 1, иначе файл отвергается при
старте), но модель всё равно его страхует: отношение «во сколько раз
очередь больше выборки» по нулевой выборке не значит ничего, поэтому два
счётчика, завязанных на выборку, не срабатывают вовсе.

Два допущения, на которых стоит эта цифра:

- она предполагает, что каждая готовая строка **проходит** проверку и
  уходит из карантина. Непрошедшая повторную проверку переставляется
  по `recheck_delays_secs` и остаётся в очереди, так что на больной
  очереди реальное осушение медленнее смоделированного;
- рекомендация это минимальное изменение, которое модель может
  подтвердить как улучшение, а не обещание попасть в цель.

Если `drain_minutes` больше `[probe].backlog_target_drain_minutes`
(по умолчанию 60, см. [раздел 8](#8-справочник-по-конфигурации)), баннер
предлагает значения; каждое из них только тогда, когда можно показать, что оно
помогает, и все они считаются последовательно, чтобы применённый вместе набор
был согласован:

- `sample_size`, ограниченный и 500, и числом строк, которые реально
  готовы (бо́льшая выборка забрала бы ровно столько же строк), и только
  когда `due_count > sample_size` плюс 20 % запаса к текущему значению;
- `concurrency`, только когда модельная полоса длиннее интервала;
  значение это наименьшее `c ≤ 64`, возвращающее полосу внутрь интервала
  **при текущей выборке или только что рекомендованной**: рекомендации
  связаны между собой, поэтому применение обеих оставляет цикл в
  графике;
- `cycle_interval_secs`, только когда укороченный период всё ещё
  вмещает модельную полосу, и никогда ниже 5 с: это тот же порог, что
  демон держит для собственного периода heartbeat, так что баннер не
  советует гонять цикл быстрее той частоты, которую сам считает
  разумной.

**Что не помогает при бэклоге.** `fail_limit`, `recheck_delays_secs`,
`second_chance_min_hours`, `second_chance_spread_hours`,
`queue_stale_days` и бэкофф `[meow]` управляют *притоком* или
внешними сервисами; осушить уже существующую очередь они не могут.
Они по-прежнему полезны, чтобы новые фейлы не копились, но это ручки
притока, а не пропускной способности.

**Пример расчёта.** С дефолтами (`sample_size = 50`, `cycle_interval_secs = 60`,
`concurrency = 8`, `connect_timeout_secs + tls_timeout_secs = 20 с`,
`target = 60 мин`) и когда все строки готовы к проверке:

| в карантине | берётся за цикл | период | осушение | баннер |
|------------:|----------------:|-------:|---------:|--------|
| 800 | 50 | 140 с | 38 мин | warning: `due_overflow`; осушение укладывается в цель, рекомендаций нет |
| 4 000 | 50 | 140 с | 187 мин | warning + `sample_size = 156` + `concurrency = 52` |
| 10 000 | 50 | 140 с | 467 мин | warning + `sample_size = 389`, без рекомендации по параллелизму: даже при `concurrency = 64` полоса из 389 строк — это `ceil(389/64) × 20 = 140 с`, все еще выше периода в 60 с (при текущем `concurrency = 8` такая полоса занимает 980 с) |
| 100 000 | 50 | 140 с | 4 667 мин | warning + `sample_size = 500` (потолок), без рекомендации по параллелизму, так же |

При `backlog_target_drain_minutes = 15` очередь в 4 000 строк
просит потолок 500 и всё равно осушается 168 минут. При худшем случае
20 с на проверку пропускная способность упирается в
`concurrency / check` строк в секунду, то есть жёсткая цель это
ограничение по пропускной способности, а не по расписанию.

**Два правила, о которых стоит знать.** И карточка демона, и баннер
бэклога считают heartbeat мёртвым после `max(period, 5) × 3`, где
`period`: это период, который демон сам сообщает в своём heartbeat
(запись, сделанная до появления этого поля, откатывается к
`heartbeat_interval_secs` этого сервера), поэтому сервер и probe с
разными файлами конфига всё равно меряют по фактическому расписанию
демона. `.max(5)` повторяет собственный период биения демона, поэтому
период меньше 5 с не может выдать живой демон за мёртвый. И
`queue_stale_days = 0` в баннере ведёт себя как 1, ровно как в ротации
демона.

## 11. Гео-обогащение

Fumox может добавлять географическую информацию к отображаемым именам прокси,
используя бесплатные базы MaxMind GeoLite2.

**Настройка:**

Ручная установка (например, со своей лицензией MaxMind) выполняется так:

1. Зарегистрируйтесь (бесплатно) на
   <https://www.maxmind.com/en/geolite2/signup>.
2. Скачайте нужную базу через
   [Account → Manage License Keys / Download Databases](https://dev.maxmind.com/geoip/docs/databases/).
3. Положите файл в `[geo].db_dir` под каноническим именем:
   `GeoLite2-City.mmdb` или `GeoLite2-ASN.mmdb`. По умолчанию это `config/`
   рядом с бинарником, то есть на хосте `./config` под Compose, **но**
   поставляемый стек Compose переопределяет `[geo].db_dir` на `/shared/geo`,
   поэтому файл, положенный в `./config`, там никогда не прочитается.
   Под Compose кладите `.mmdb` в том `fumox-geo` (`/shared/geo`) либо
   уберите переопределение `FUMOX_GEO__DB_DIR` из `docker-compose.yml` и
   задайте `[geo].db_dir` в файле. Этот шаг вообще можно пропустить: Fumox
   скачивает базы сам (ниже), и под Compose эта загрузка уже идет в
   `/shared/geo`.

Fumox открывает **все** базы, которые находит в `[geo].db_dir`, и объединяет
их факты, поэтому страна, город и ASN-данные сочетаются в одном шаблоне
имени. База Country не используется: все ее факты есть в City (лежащий
рядом старый `GeoLite2-Country.mmdb` просто игнорируется). Если ни одну
базу открыть не удалось, гео-обогащение тихо отключается (в лог пишется
предупреждение), все остальное продолжает работать. MaxMind обновляет базы
еженедельно.

Fumox может скачать базы сам: при старте сервер проверяет `[geo].db_dir` и
загружает отсутствующие, поврежденные или старше месяца базы GeoLite2 с
публичного зеркала релизов. На эту загрузку сервер ждет не дольше
`[geo].startup_download_budget_secs` (60 с, потолок 300 с) и только потом
начинает принимать соединения: медленное зеркало не держит сервис в простое:
загрузка продолжается в фоне, а результат подхватывается при следующем
старте. Скачивание можно выключить целиком: `[geo].auto_download = false`, и
тогда файлы кладет оператор.

**Откуда берутся файлы.** Встроенное зеркало — это публичные ассеты релизов
P3TERX (`https://github.com/P3TERX/GeoLite.mmdb/releases/latest/download/GeoLite2-City.mmdb`
и то же для `GeoLite2-ASN.mmdb`), поэтому дефолту **не нужен** ни аккаунт
MaxMind, ни лицензионный ключ. Ключ MaxMind нужен только если вы укажете в
`[geo].download_urls` сервера самого MaxMind: их загрузки аутентифицированы, и
ключ тогда живет в URL или в basic auth сервера. Зеркало может быть и недоступно
(лимит запросов, сетевой блок, убранный ассет релиза): загрузка падает, лог
называет файл и причину, а запуск продолжается без гео-обогащения. В этом
случае положите `.mmdb` в `[geo].db_dir` руками — под Compose это том
`fumox-geo` (`/shared/geo`) — либо укажите в `[geo].download_urls` другое
зеркало.

Скачанный файл проверяется до установки: если для него указана сумма в
`[geo].sha256`, база ставится только когда скачанный файл ей соответствует, а
при несовпадении прежняя база остается на месте. Файл без указанной суммы
проверяется по метаданным MaxMind: валидная база другого провайдера
остается, отбраковывается только битый файл или HTML-страница с ошибкой.

**Здоровье.** `/healthz` отвечает двумя строками: первая говорит, отвечают ли
процесс и база, вторая называет состояние гео
(`geo: off | no databases | degraded | ready`). `degraded` — база открыта, но не
та, что несет страну (только ASN), то есть в именах есть номер AS, а страны
нет. Единственная жесткая зависимость от гео — allowlist стран у профиля: при
включенном гео такой профиль и отсутствие базы City abort старт с сообщением,
называющим состояние и каталог.

**Шаблоны имен.** Настройка pipeline `geo.template` (по умолчанию
`"{flag} {country} · {name}"`) поддерживает плейсхолдеры; все они работают
в одном шаблоне одновременно, каждый берет данные из своей базы:

| Плейсхолдер | Значение                             | Источник данных |
| ----------- | ------------------------------------ | --------------- |
| `{flag}`    | Эмодзи-флаг страны                   | База City       |
| `{country}` | Название страны (fallback: ISO-код) | База City       |
| `{city}`    | Город                                | База City       |
| `{asn}`     | Номер AS в виде `AS12345`            | База ASN        |
| `{asn_org}` | Название организации AS              | База ASN        |
| `{name}`    | Исходное отображаемое имя            | –               |

Плейсхолдер без данных схлопывается в ничто: лишние пробелы и висящие
разделители убираются, поэтому `"{flag} {country} {city} · {name}"` выглядит
аккуратно, даже когда город неизвестен. Имя остается полностью нетронутым,
только если гео-данных нет вообще. DNS- и гео-запросы кэшируются (хосты часто
повторяются): имя, которое не разрешилось, кэшируется всего на десять минут,
хост, которого нет в базах, — как и известный, на шесть часов.

Неизвестный плейсхолдер отвергается там, где сохраняется шаблон: и панель,
и загрузчик конфига, поэтому опечатка не превратится в литеральный `{foo}` в
каждом имени прокси. Шаблон без `{name}` получает исходное имя в конец, пустой
шаблон выводит одно имя.

**Сохранение гео-фактов.** Определенные для прокси страна, город и ASN
записываются в базу при инжесте, а при старте сервера фоновый проход
дополняет прокси, занесенные до появления базы. На этих данных работает
админка: фильтр по стране в списке *Прокси* и блок *География* в карточке
показывают сохраненные факты, они заполнятся после ближайшего обновления
источника или перезапуска сервера, даже если подписку еще никто не
запрашивал. Свежий пустой результат никогда не стирает уже сохраненные
факты. Хост, чей запрос не ответил, помечается и не трогается шесть часов,
прежде чем фоновый проход попробует снова: неразрешимые хосты не забирают
бюджет прохода у строк, которые не пробовали вообще.

## 12. Данные, резервные копии, ротация

- **Хранилище.** Один файл SQLite в режиме WAL. Внутри креденшелы прокси в
  открытом виде: файл создается с правами `0600`, держите доступ к каталогу
  ограниченным.
- **Резервные копии.** Используйте WAL-безопасный онлайн-бэкап, а не сырое
  копирование файла:

  ```bash
  sqlite3 fumox.db ".backup /backups/fumox-$(date +%F).db"
  ```

- **Контроль роста.** Probe автоматически чистит историю: `probe_results`
  старше 14 дней и `fetch_log` старше 30 дней по умолчанию (`[retention]`).
  Общие журналы сервер чистит и сам — `fetch_log` и `probe_requests` с
  каденцией `[probe].retention_interval_secs`, — так что развёртывание без
  probe-демона остается ограниченным тоже. Удаленные прокси накапливаются,
  пока вы не нажмете *«Стереть удалённые»* в админке.
- **Бэкап конфигурации.** Используйте *Экспорт* в админке: он собирает все
  источники и профили в JSON-файл, который можно импортировать на другом
  инстансе.
- **Временные метки** везде хранятся как Unix epoch в секундах, UTC; админка отображает
  их в часовом поясе вашего браузера (см. *Время и часовые пояса*).

### Бэкапы под Docker Compose

Под Compose база лежит не в каталоге проекта, а в томе `fumox-data`,
который смонтирован в `/app/data` и в контейнер server, и в контейнер
probe, как `/app/data/fumox.db` (образ задает этот путь через
`FUMOX_DATABASE__PATH`). Поэтому бэкап нужно снимать внутри контейнера
с тем же томом, и ему нужна утилита `sqlite3`, которой в поставляемом
образе нет (там SQLite подключена как библиотека). Одноразовый контейнер
сервиса server уже видит этот том и может поставить утилиту на время
запуска:

```bash
STAMP="$(date +%F)"
mkdir -p backups
docker compose run --rm --no-deps --user root \
  -v "$PWD/backups:/backups" \
  --entrypoint sh server \
  -c "apt-get update >/dev/null && apt-get install -y --no-install-recommends sqlite3 >/dev/null && sqlite3 /app/data/fumox.db '.backup /backups/fumox-${STAMP}.db'"
```

Установке нужен интернет — один раз; дальше образ кеширует слой. То же
работает с любым образом, в котором есть утилита `sqlite3`.

**Копирование `fumox.db` — это не бэкап.** База работает в режиме WAL:
новые строки могут лежать в `fumox.db-wal`, поэтому копия одного основного
файла их не содержит, а копия, снятая во время записи, может быть
рваной. Команда `.backup` выше пишет согласованный снимок живой базы;
альтернатива — остановить сервер и probe, а затем скопировать вместе
`fumox.db`, `fumox.db-wal` и `fumox.db-shm`.

### Скрипты восстановления и починки

В репозитории есть три операторских инструмента. Все они сначала делают
бэкап и все они отказываются писать поверх того, чего не поняли.

- **`scripts/revive-xhttp-proxies.sh --restore <бэкап> [база]`** кладет бэкап
  обратно на место базы. Скрипт отказывает на отсутствующем пути (`код 66`),
  на пустом, поврежденном (`PRAGMA integrity_check`), посторонней-схемы или
  симлинк-бэкапе (`код 67`), и отказывает работать, пока база еще открыта
  кем-то другим (`код 75`), если только `FUMOX_REVIVE_CONFIRM_STOPPED=1` не
  подтверждает, что демон действительно остановлен. Копия сначала
  разворачивается рядом с базой и переименовывается на место, затем ее
  размер сверяется с бэкапом, и короткая копия откатывается на снимок,
  сделанный скриптом до этого. При любой ошибке печатаются путь снимка и
  готовая команда откката.
- **`scripts/repair-geo-stamps.sh [база]`** очищает колонки `geo_*`, чтобы
  стартовый бэкфилл заново определил их по собственному хосту каждой
  строки. **Остановите сервер (и probe) перед запуском и перезапустите
  сервер после** — именно перезапустите, а не просто запустите: бэкфилл
  работает в начале процесса. Скрипт отказывается работать, пока виден
  процесс сервера или probe.
- **`cargo run -p fumox-core --example repair_migration_checksums -- <база>`**
  переподписывает чек-сумму примененной миграции, чей файл изменился после
  применения. Утилита отказывает на «грязной» (упавшей) миграции и на
  версии, которая никогда не применялась, и завершается с ошибкой, если
  не удалось сделать checkpoint журнала упреждающей записи. Альтернатива —
  `[database].allow_checksum_repair = true` на один запуск.

Миграции сервера и probe сериализуются файлом блокировки рядом с базой
(`fumox.db-migrate.lock`): запущенные в один момент, оба процесса иначе
пытались бы применить одну и ту же миграцию дважды. Блокировка
согласованная и снимается при выходе процесса, так что файл можно спокойно
оставлять на месте.

## 13. Продакшен – контрольный список

- [ ] Задайте сильный `[admin].token` (в комплекте токен пустой, и панель
      остается выключенной — 404 — пока не задан настоящий; под Compose
      `FUMOX_ADMIN__TOKEN` обязателен); `secure_cookies = true` за HTTPS.
- [ ] Слушатель админки остается на loopback; внешний доступ только через
      TLS reverse-proxy или SSH-туннель.
- [ ] **За reverse-proxy:** задайте `[server].trust_proxy_ips` и
      `[admin].trust_proxy_ips`: CIDR прокси-сервера (например,
      `["127.0.0.1/32"]` для nginx на том же хосте, либо подсеть
      внешнего прокси). Без этих ключей все запросы делят один IP и
      лимит по IP превращается в один общий бюджет на весь трафик.
- [ ] **За reverse-proxy:** задайте `[server].trust_proxy_header` и
      `[admin].trust_proxy_header` — семейство заголовков, которое пишет
      прокси (`"xff"`, `"forwarded"` или `"both"`). По умолчанию `"none"`
      не читает ни одного forwarding-заголовка, поэтому ключ rate-limit
      считается по IP прокси, а схема в отрисованных ссылках остается
      `http` даже за TLS-терминирующим прокси. О стартовом логе с таким
      предупреждением сказано в журнале запуска.
- [ ] **За reverse-proxy:** задайте `[server].allowed_hosts` и
      `[admin].allowed_hosts`: публичное имя хоста (например,
      `["fumox.example.com"]`). Без этих ключей `Host`-заголовок
      принимается как есть при формировании URL в админке и в
      токенах `/export/alive/{token}` / `/export/ready/{token}`,
      атакующий, способный подменить `Host`, добьется того, что
      админка отрисует URL на свой домен и уведет токен. Задайте
      эти ключи в любом развертывании, работающем под фиксированным
      доменным именем. Если панель открывается на *другом* хосте, чем
      публичный слушатель (loopback, дефолт Compose), добавьте этот хост
      ещё и в `[server].allowed_hosts`: ссылка на alive/ready за
      *Импорт/экспорт*, *Источники* и *Профили* строится по хосту, по
      которому открыта панель, а публичный слушатель отвечает `404` на
      хост, которого не обслуживает. Сами три экрана отрисовываются.
- [ ] **За reverse-proxy:** прокси пробрасывает исходный заголовок `Host`
      без изменений (nginx: `proxy_set_header Host $host;` — готовый
      пример `docker/nginx/` уже так делает). Админка отвечает `403`
      (`err.cross_site`) на запросы, классифицированные как
      кросс-сайтовые, до авторизации, CSRF и rate-limit:
      `Sec-Fetch-Site: cross-site` (переходы верхнего уровня на
      `/admin` исключены), `Origin: null` либо `Origin`, чей host:port
      не совпадает с `Host`. Браузеры с собственного источника панели и
      клиенты без заголовков не затронуты; прокси, переписывающий
      `Host`, или не-браузерная интеграция, которая POST-ит с чужим
      `Origin`, получает `403` там, где раньше запрос обрабатывался.
- [ ] `allow_private_urls` переведен в `false` (встроенный дефолт, SSRF-защита).
      В поставляемом примере `config/app.toml` стоит `true`, поэтому поменяйте
      его, если у вас нет конкретной причины доверять внутренним источникам.
      А вот `[probe].allow_private_targets` такой проверки не требует:
      в примере он поставляется как `false`, вровень со встроенным дефолтом,
      а `true` это осознанный опт-ин для изолированного тестового стенда.
- [ ] Один `fumox-server` + один `fumox-probe` на один файл базы;
      `busy_timeout_ms` не убран.
- [ ] meow-rs работает как собственный долгоживущий сервис (systemd-юнит /
      контейнер с restart-политикой), REST API на `[meow].api_addr`;
      `[meow].config_path` читаем для процесса meow-rs.
- [ ] `[meow].test_url` доступен из сетей ваших прокси.
- [ ] Гео-обогащение работает: сервер сам скачивает базы GeoLite2 в
      `[geo].db_dir`, если каталог доступен для записи (под Compose это
      `/shared`, а не `./config`), — если нужны гео-имена, убедитесь, что
      они появились в названиях узлов.
- [ ] Регулярные бэкапы БД через `sqlite3 ".backup"`.
- [ ] Супервизор процессов с автоперезапуском (systemd, Docker
      `restart: unless-stopped` и т.п.). Оба бинарника корректно завершаются
      по SIGTERM.

Минимальный набросок systemd-юнита:

```ini
# /etc/systemd/system/fumox-server.service
[Unit]
Description=Fumox subscription server
After=network-online.target

[Service]
ExecStart=/opt/fumox/fumox-server --config /etc/fumox/app.toml
WorkingDirectory=/opt/fumox
Restart=always
User=fumox

[Install]
WantedBy=multi-user.target
```

(Probe получает идентичный юнит с `fumox-probe` и тем же
`WorkingDirectory=/opt/fumox`; meow-rs свой собственный.)

`WorkingDirectory` — не украшение: любой относительный путь в конфиге
разрешается от рабочей директории процесса (см. *Куда указывают
относительные пути*), поэтому юнит без него разрешает относительные пути
от `/`.

## 14. Решение проблем

| Симптом                                                      | Вероятная причина / решение                                                                                                                           |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Админка везде отвечает 404                                   | `[admin].token` пуст или `enabled = false`: панель намеренно неактивна. Задайте токен и перезапустите.                                                |
| Админка не видна с другой машины                             | Она слушает `127.0.0.1` по замыслу. Используйте `ssh -L 8081:127.0.0.1:8081 host` или reverse-proxy.                                                  |
| После успешного входа снова редирект на `/admin/login`         | `[admin].secure_cookies` включен, а панель открыта по plain HTTP (`http://127.0.0.1:8081`): браузер выбрасывает cookie с флагом `Secure`, и сессия не доходит. Задайте `FUMOX_ADMIN__SECURE_COOKIES=false` в `.env` (compose ставит `true`) или `[admin].secure_cookies = false` и войдите снова. |
| Админка отвечает 403 (`err.cross_site`)                      | Запрос классифицирован как cross-site (`Sec-Fetch-Site: cross-site`, `Origin: null` или `Origin`, чей host:port не совпадает с `Host`). За reverse-proxy пробрасывайте `Host` без изменений и отправляйте собственный origin панели; небраузерный клиент, который шлет `Origin`, должен назвать origin панели или не слать заголовок вовсе. |
| `/sub/…` возвращает 403                                      | У профиля задан токен доступа: добавьте `?token=…` или заголовок `Authorization: Bearer`.                                                             |
| `/sub/…?format=clash` возвращает 400                         | `?format=` запрещен по замыслу. Создайте отдельный профиль с нужным форматом.                                                                         |
| Пустая подписка с `X-Fumox-Warning: all-proxies-quarantined` | Все прокси провалили проверки. Загляните на страницу *Probe* и в историю проверок; проверьте доступность `[meow].test_url`.                           |
| Заголовок `X-Fumox-Stale: true`                              | Часть источников временно недоступна; отдаются последние хорошие данные. Журнал загрузок покажет, какие источники и почему (`error_class`).           |
| У источника `parse_error`                                    | Источник вернул HTTP 200, но контент не разбирается (анти-бот-страница, заглушка CDN, смена формата). Тем временем отдается последний хороший снимок. |
| У источника `storage`                                       | Фид ответил HTTP 200, но процесс не смог сохранить результат: база отказала в записи. Это сбой на нашей стороне, а не на стороне источника. |
| Источник не сохраняется: ошибка «private URL»                | URL резолвится в loopback/приватный адрес, а `allow_private_urls = false`. Так работает SSRF-защита.                                                  |
| Нет флагов стран в именах                                    | Файла GeoLite2 `.mmdb` нет в `[geo].db_dir` либо `[geo].enabled = false`. Под Compose это каталог `/shared/geo`, а не `./config`, см. [раздел 11](#11-гео-обогащение). Состояние гео называет вторая строка `/healthz` (`geo: off \| no databases \| degraded \| ready`). |
| *Импорт/экспорт*, *Источники* или *Профили*: ссылка 404                | Ссылка строится по хосту, по которому открыта панель, а публичный слушатель отвечает `404` на хост, которого не обслуживает. Добавьте этот хост в `[server].allowed_hosts` или откройте панель по имени хоста, который слушатель уже обслуживает. |
| Файл GeoLite2 в `./config` игнорируется                       | Стек Compose задает `FUMOX_GEO__DB_DIR=/shared/geo`, а окружение приоритетнее `config/app.toml`. Кладите базы в том `fumox-geo` или уберите переопределение и задайте `[geo].db_dir`. |
| Загрузка GeoLite2 падает (`GeoLite2 database download failed`) | Зеркало недоступно, отдаёт лимит запросов или его ассет релиза убран. Положите файлы `.mmdb` в `[geo].db_dir` руками (`GeoLite2-City.mmdb`, `GeoLite2-ASN.mmdb`; под Compose это том `fumox-geo`, `/shared/geo`), укажите в `[geo].download_urls` другое зеркало или задайте `[geo].auto_download = false` и принесите файлы сами. См. [раздел 11](#11-гео-обогащение). |
| T2-проверки не идут, в логе probe backoff meow               | meow-rs лежит или неверен `[meow].api_addr`. В Docker это должен быть `meow:9090`; путь к конфигу общий том (`/shared/meow.yaml`).                    |
| Ошибки `SQLITE_BUSY` в логах                                 | `busy_timeout_ms` убран или слишком мал, а в базу пишут два процесса. Верните дефолт (30000).                                                          |
| Сервер не стартует: «applied migration N differs from the file» | Файл миграции изменился после того, как был применен. Переподпишите эту версию утилитой `cargo run -p fumox-core --example repair_migration_checksums -- <путь к базе>` или запустите один раз с `[database].allow_checksum_repair = true`. |
| `scripts/revive-xhttp-proxies.sh --restore` завершился с кодом 75 | База еще кем-то открыта. Остановите демон (`docker compose stop server probe`) и повторите; `FUMOX_REVIVE_CONFIRM_STOPPED=1` снимает проверку, если вы уверены, что демон остановлен. |
| `scripts/revive-xhttp-proxies.sh --restore` завершился с кодом 67 | Бэкап пуст, поврежден или не является базой Fumox. Ничего не тронуто: возьмите другой бэкап. |
| Страна / ASN на старых строках неверны                         | Строки, загруженные до 2026-10-02, несут гео-штампы соседнего хоста. Запустите `scripts/repair-geo-stamps.sh` при остановленном сервере, потом перезапустите сервер. |
| Сборка падает: `sqlite3.h: No such file`                     | Установите системный dev-пакет SQLite (`libsqlite3-dev` на Debian/Ubuntu).                                                                            |
| Compose отказывается стартовать: «set FUMOX_ADMIN__TOKEN»    | Создайте `.env` из `.env.example` и задайте токен.                                                                                                    |
